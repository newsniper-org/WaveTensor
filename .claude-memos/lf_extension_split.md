# `Lf` 확장의 분할 — `Lf64min` / `Lf64di`

> ### 📌 지위 — 비정본. 사용자 결정의 기록이며 설계는 아직 없다.
>
> 정본은 `docs/wt64v1-architecture-guide/` 하나이고 이 문서의 어떤 문장도
> 계약이 아니다. 여기 적힌 것 중 정본에 들어간 것은 **0건**이다.

## 1. 사용자 결정 (2026-08-28)

> **`Lf`(f64 지원 추가) 확장은 `Lf64min`(f64 지원 그 자체만 추가) 확장과
> `Lf64di`(`Di` 의 f64 버전) 확장으로 분할한다.**

선행 결정과의 관계 — f64 를 base 밖으로 낸 것은 2026-07-16 사용자 결정이다
(「f64 → 별도 optional extension `Lf` 로 이관, 완전 컷 아님」). base 는
dtype 니블 `0x5` 를 `decode_error` 로 예약하고 `Lf` 가 나중에 claim 한다.
**이번 결정은 그 하나짜리 `Lf` 를 둘로 가르는 것이다.**

## 2. 분할이 사는 축 — 왜 이것이 옳은 모양인가

둘의 **전건이 다르다.** 이것이 분할의 실질이다.

| | `Lf64min` | `Lf64di` |
|---|---|---|
| 무엇 | f64 데이터 형식과 그 산술 | `Di` 미적분 연산의 f64 판 |
| 전건 | 없음 — 독립적으로 값이 있다 | **`Di` 확정안의 착지**(`di_design_v1.md`) |
| 소비자 | 과학계산 일반 (선형대수·ODE/PDE·통계) | `Di` 의 소비자 중 f64 를 요구하는 것 |
| 좁게 시작 | 가능 — dtype `0x5` 하나 claim | 불가 — `Di` 축 넷에 각각 붙는다 |

정본 규율과 정합한다 — **「좁게 시작해서 넓히는 것은 언제나 가능하고 그 반대는
불가능하다」**(@sec:isa 1.4.2 해설). 하나짜리 `Lf` 는 f64 산술과 미적분 f64 판을
한 덩어리로 묶어 **둘 중 하나만 필요한 소비자에게 나머지를 강매**한다.
그리고 `Lf64di` 는 `Di` 가 아직 확정 전이므로 **전건이 서지 않은 채로 설계에
끌려들어간다** — 하나로 두면 `Lf` 전체가 `Di` 를 기다리게 된다.

## 3. ⚠️ 분할이 즉시 부딪히는 벽 — dtype 니블에 자리가 없다

**이것이 이 문서를 지금 쓰는 실질적 이유다.** 실측(2026-08-28,
`isa/wt64v1_isa.json`):

```
dtype_codes = { int4:0, int8:1, f16:2, bf16:3, f32:4,
                f64_reserved_Lf:5, q4_4:6, q8_8:7 }
```

그리고 손-핀 불변식(`fp_block._doc`, 「hand-pinned in tests,
**generator-independent**」)이 **`dtype > 0x7` 을 전역 불법**으로 못박는다.
⇒ **4비트 니블 여덟 칸이 전부 이름을 갖고 있다.**

- `Lf64min` 은 문제없다 — `0x5` 가 그 이름으로 예약돼 있고 claim 하면 끝이다.
- **`Lf64di` 는 자리가 없다.** `Di` 1차 확정안이 `dual_f32` 를 `0x6` 에
  배정했는데(그 근거는 「fp 블록 ops 열넷의 `legal_dtypes` 가 `{0,1,2,3,4}`
  뿐이라 `0x6`·`0x7` 을 아무도 안 쓴다」— **실측으로 참이다**), `dual_f64` 를
  같은 방식으로 두려면 남은 칸이 `0x7`(q8_8) 하나이고 그마저 이름이 있다.

### 3.1 여기서 갈래가 셋이고, 셋 다 대가가 다르다

1. **손-핀 완화** — `dtype > 0x7` 을 열어 `0x8`+ 를 쓴다. `Di` 확정안이 이미
   판정한 대로 「그 불변식의 **명시적 완화**이고 생성기 밖 테스트를 함께
   움직여야 한다」. 니블이 4비트이므로 `0x8`–`0xF` 여덟 칸이 열린다.
2. **dual 을 dtype 축에서 빼기** — dual 여부를 mode byte 의 **다른 필드**로
   나른다. `Di` 확정안의 실측이 여기서 값을 갖는다: **`acc`(2b)·`rnd`(2b)는
   각각 4값 중 1값만 합법이라 여유가 상당하다.** 그러면 `dual × dtype` 이
   직교하고 `dual_f64` 가 자동으로 따라온다 — **`Lf64di` 가 dtype 을 한 칸도
   안 먹는다.** 대가는 `Di` 확정안의 `0x6` 배정을 되돌리는 것.
3. **f64 dual 을 별도 opcode 로** — dtype 축을 안 건드리지만 opcode 를 먹고,
   `Di` 확정안이 「연산마다 opcode 로 미끄러진다」며 기각한 형태에 가깝다.

**갈래 2 가 유력해 보이나 재지 않았다.** `Di` 확정안이 dual 을 dtype 으로 둔
근거는 「정본이 이미 이름한 기구 — *명령이 정밀도를 지정하고 데이터패스가 그에
따라 자릿수와 반올림을 바꾼다*」(@sec:fabric 2.5)인데, 그 논거는 `acc`/`rnd`
필드에도 그대로 선다(셋 다 같은 mode byte 안이다). **어느 필드가 옳은 자리인지는
`Di` 재검토가 답할 것이고, 이 분할이 그 질문을 강제한다.**

### 3.2 같은 코드점이 두 이름을 갖는 문제 — 별개로 남는다

`Di` 확정안이 `0x6` 을 쓰면 그 코드점은 **fp 블록 안에서 `dual_f32`, 밖에서
`q4_4`** 가 된다. 「어느 fp 블록 행도 안 쓴다」는 실측은 참이지만, 정본이
경계하는 형태 — 「**같은 비트가 어느 계약을 뜻했는지 알 수 없게 된다**」
(@sec:isa 1.4.2, 스레드 ID 폐지의 근거) — 에 걸리는지는 확정안이 다루지 않았다.
**`Di` 재검토의 안건이다.** 갈래 2 를 고르면 이 문제도 함께 사라진다.

## 4. 아직 아무것도 정해지지 않은 것

- **`Lf64min` 의 범위** — f64 산술을 어느 opcode 에 legal 로 더하는가.
  fp 블록 열넷 중 어디까지인가. `0x7A FDOT32_CR` 의 값 계약(비트 동일 축약)이
  f64 로도 서는가 — **`Di` 리만 축이 그 계약에 통째로 기대므로 `Lf64di` 의
  리만 판이 여기 걸린다.**
- **`Lf64di` 의 축별 범위** — `Di` 네 축(리만·르베그·Forward AD·Stencil) 중
  어느 것이 f64 판을 갖는가. 전부인가 일부인가.
- **페이로드 폭** — f64 4레인이면 256b 이고 조각 수가 f32 대비 2배다.
  `FRAG_MAX` 와 `CAP_STATUS[0]`(재조립 슬롯) 축에 어떻게 걸리는가. 재지 않았다.
- **dtype 자리 갈래 셋 중 무엇** (§3.1) — `Di` 재검토와 함께 답해야 한다.
- **두 확장의 순서** — `Lf64min` 이 `Lf64di` 의 전건인가, 독립인가.
  (전건으로 보이나 확인 안 됨.)
- 두 확장의 지위 — `WT64v1-C` 계열인가 `v2.x` 인가. `wt64v1c_extension_plan.md`
  의 지위 판정이 `T_stable` 재정의에 걸려 연기돼 있고 같은 질문이 여기 붙는다.
