# on-wire 포맷 (WebRTC data channel) — 사용자 제안과 평가

> ### 📌 지위 — 사용자 제안(2026-08-28)의 기록 + 평가. 설계는 #27 몫이다.
>
> 정본은 `docs/wt64v1-architecture-guide/` 하나이고 이 문서의 어떤 문장도
> 계약이 아니다. 제안의 비트 배치가 대화에만 있었으므로 즉시 기록한다 —
> 「기록되지 않은 미결은 미결이 아니라 분실이다」.

## 1. 제안 원문 (2026-08-28) — 충실히 옮김

파이프라인 끝에 **#27** 을 추가한다:

- **#25 완료 시점의 [페이로드+명령어] 포맷을 「기본 포맷 겸 in-flight 포맷」
  으로 정의**하고, 거기서 **CRC "만" 제외한 나머지 비트스트림에 1:1 대응되는
  on-wire 포맷**을 별도로 새로 정의한다.
- **WebRTC data channel 용. ⚠️ 무조건 big-endian 직렬화.**
- **첫 바이트 상위 니블 = 플래그 전용 영역 (역할 고정)**:
  - 첫 2비트: **Remote Direct Execution 모드 플래그** —
    「단순 가상 메모리 쓰기」(DVMA Store) XOR
    「쓰기 후 즉시 PC 를 해당 위치로 점프시키는 실행 트리거」
    (DVMA Store-and-Execute)
  - 나머지 2비트: 다른 플래그용 예약
- **opcode 배치** (기본 포맷은 `[31:24]` + `[11:8]` 분할):
  - 첫 바이트 하위 니블 ⟷ 기본 헤더 `[11:8]` (확장 니블 — **영역이 먼저 온다**)
  - 둘째 바이트 전체 ⟷ 기본 헤더 `[31:24]`
- 셋째 바이트 ⟷ 기본 헤더 `[23:16]` (next_hdr 4 + flags 4)
- 넷째 바이트 ⟷ 기본 헤더 `[7:0]` (bh_len)
- **다섯째 바이트 = EH 별 워드 길이**:
  `[7:6]` EH1 · `[5:4]` EH2 · `[3:2]` EH3 · `[1:0]` EH4 (없으면 `0b00`)
- EH 길이 총합에 따라 **패킷 길이를 동적으로 끊어** 보낸다.

## 2. 평가 — 잘 앉는 지점 셋

**① CRC 제외는 옳은 계층화이고, #26 의 결과에 불변이다.**
wire 구간은 WebRTC 의 DTLS/SCTP 무결성이 덮고, in-flight CRC(W5 OPREF ·
#26 이 채택할 수 있는 것들)는 **ingress 에서 재계산**된다 — 각 층의 검사가
자기 구간을 덮는 고전적 배치다. 부수 효과가 크다: CRC 를 아예 안 나르므로
**#26 이 무엇을 채택하든 on-wire 포맷은 안 바뀐다.** 기본 헤더 `[15:12]` 를
wire 가 안 나르는 것도 같은 원리로 무손실이다 — 수신측이 CRC(채택 시) 또는
0(미채택 시)으로 재구성한다.

**② 다섯째 바이트는 이 저장소의 검산 관용구 그 자체다.**
EH 워드 수는 in-flight 에 이미 두 겹으로 있다(각 EH 첫 워드 `[7:0]` ·
bh_len 총합). wire 의 길이 벡터는 셋째 선언이고, **삼중 선언 교차 검산**
(authority/검산/안전장치 — §4.2 관용구)이 wire 층까지 연장된다. ingress 가
셋을 대조하면 wire 절단·프레이밍 오류가 구조로 잡힌다.

**③ 2비트 × 4 가 정확히 맞는다 — 우연이 아니라 실측이다.**
EH 워드 길이 실측 최대 3 (IMM64), 2비트로 0(부재)·1·2·3 정확 표현.
기본 형상 EH ≤ 4 라 4칸 = 1바이트 정확 적합. 그리고 첫 두 바이트에
**12b opcode 전체가 영역 니블 먼저** 오므로 wire 레벨에서 영역 분류가
1바이트 읽기로 된다.

## 3. 설계 질문 다섯 — #27 이 답해야 한다

**Q1 (제1 계약) — Store-and-Execute 는 §2.3 을 보존해야 한다.**
이 기계에 PC 는 없다 (§2.3: 「PC 도 fetch 도 재발행도 장치 주도 재투입
기구도 없다」). 「PC 를 해당 위치로 점프」는 envelope 층(수신 호스트)의
의미론이며, 가속기에 대해서는 **반드시 「명령 링 투입」으로 사상**되어야
한다 — wire 의 실행 트리거가 호스트 큐를 우회하는 둘째 발화 원천이 되는
순간 §2.3 위에 선 다섯이 전부 흔들린다. DVMA 축(HIU 의 플랫폼 독립 역할,
`remote_accelerator_access.md` 계보)과의 접면 정의가 #27 의 첫 일이다.

**Q2 — ~~CRC 제외의 입도~~ 해소 (사용자 확인 2026-08-28): 「1:1 대응」은
비트 재배치다.** 0-채움이 아니다 — wire 는 CRC 비트를 **아예 나르지 않고**,
남은 비트 전체를 재배치한 진짜 전단사다. 초판이 「0-채움 유력」이라 적은
것은 사용자 의도가 아니었다.

**주신 헤더 배치가 이미 그 증명이다** — 기본 헤더 32b 에서 `[15:12]` 4b 를
빼면 28b 이고, envelope 플래그 4b 를 더하면 정확히 32b = 4바이트다:
byte1(플래그 4 + ext 4) + byte2(opcode 8) + byte3(next_hdr·flags 8) +
byte4(bh_len 8). **낭비 0비트.**

남는 하위 질문 하나: OPREF 워드는 CRC 니블을 빼면 28b 라 EH 구역의 비트
총합이 8 의 배수가 아닐 수 있다(예: OPREF 하나면 mod 8 = 4). **패킷 말미
패딩 규칙**(길이·값·검사 여부)을 #27 이 못박아야 하고, 그와 함께 **전 비트의
자리 사상표**가 #27 의 핵심 산출물이 된다 — 헤더 5바이트는 그 표의 첫
장이다.

**Q3 — 「4 EH」는 형상 파라미터인데 wire 상수가 된다.**
정본 §1.3.1: 「이 상한은 형상 파라미터이지 ISA 상수가 아니다.」 다섯째
바이트가 4 를 굳히면 **정본이 인코딩에서 몰아낸 형상 상수를 wire 층이
다시 들인다.** 큰 형상(EH > 4)의 구현이 오면 wire 가 표현 불가. 처방 후보:
예약 플래그 2비트 중 하나를 「확장 프레이밍 바이트 후속」으로 정의해 두기
(지금 정의하지 않아도 자리를 이름 붙여 두는 것 — §5.7 엄격 예약과 같은 결).

**Q4 — 페이로드·태그의 직렬화가 범위에 든다.**
「[페이로드+명령어] 포맷」이므로 명령어 5바이트 헤더만으로는 절반이다.
태그 80b(사이드밴드)·페이로드 beat(64b)·조각 머리(순번·총개수·마지막)의
big-endian 사상표가 필요하다. in-flight 는 리틀엔디언 워드 배치(§1.3.2)라
**필드별 바이트 순서 사상표가 정밀하게 핀**되어야 한다 (IMM64 의
w1=하위/w2=상위 같은 자리가 뒤집힘 사고의 단골이다).

**Q5 — RDE 2비트의 값 공간.**
「A XOR B」(정확히 하나)면 1비트로 족한데 2비트가 배정됐다 — `00` = RDE
아님(순수 데이터?) · `01`/`10` = Store / Store-and-Execute · `11` = ? 의
4값 공간으로 읽는 것이 자연스러우나 **`11` 의 처분**(malformation?)과
`00` 의 의미를 #27 이 못박아야 한다. 미지 값 처분은 §5.7 엄격이 관례다.

## 4. 파이프라인 위치

**#27, #25 에 blocked.** 근거: in-flight 포맷이 「#25 완료 시점」으로
지정됐다 — W1~W7(+#26 채택분)이 착지한 뒤의 포맷이 기준선이다.
CRC 제외 원칙 덕에 #26 의 *결과*에는 불변이나, **기준선 스냅숏**은 #25
뒤라야 한다.
