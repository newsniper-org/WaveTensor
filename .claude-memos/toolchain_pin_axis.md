## 1. 정본이 세운 구분 — 인용

정본 06-formal.typ:589-594 축자:

> - *내용 고정(해시·커밋)은 필요조건이다.* 없으면 「무엇으로 쟀는가」에 답할 수
>   없고, 바꿔치기가 조용히 지나간다.
> - *재현의 충분조건은 그 내용을 이쪽이 보관하는 것이다.* 상류가 계속 준다는

그리고 606행에서 스스로 인쇄한다 — **「보관본은 어느 층에도 없다. 충분조건은
축 전체에서 미달이다.」**

## 2. ⚠️ 결손의 크기를 브리프보다 크게 잡아야 한다

이 파도의 브리프는 결손을 「tla2tools.jar 4.5MB 를 어디 둘 것인가」로 놓았다.
**정본은 그보다 넓게 적어 두었고, 정본 쪽이 맞다.** 06-formal.typ:598-605 는
내용 고정조차 층마다 갈린다고 적는다 —

> 그러나 배포 스냅샷의 *날짜 좌표*로 설치되는 층은 그렇지 않다: 합성
> 프론트엔드와, 후-formal 태스크 *전부*가 명시하는 워드 수준 솔버가 여기 든다.
> (…) **날짜는 좌표이지 내용이 아니다**

⇒ `ALA_SNAPSHOT=2026/08/12` 로 깔리는 층은 **해시로 고정돼 있지도 않다.**
yosys 0.66 · z3 4.16.0 · verilator 5.050 · iverilog 13.0 · jdk21 · sbt · python
이 전부 여기 든다. 즉 보관본 논의를 jar 하나로 좁히면 **정본이 이름 붙인 결손의
대부분을 빠뜨린다.**

### 층별 실측 (2026-08-30, `localhost/wavetensor-dev:scala` 및 상류 직접 측정)

| 층 | 고정 방식 | 상류 | 분량 (실측) | 보관본 |
|---|---|---|---|---|
| tla2tools.jar | BLAKE2b-512 내용 해시 | GitHub 롤링 pre-release | **4,487,757 B** | 없음 |
| ALA 패키지 일체 | **날짜 좌표만** (내용 고정 없음) | archive.archlinux.org | 295 패키지 / 설치 후 **약 2,596 MiB** | 없음 |
| SpinalHDL·Scala·sbt 의존 | Maven 좌표 (릴리스 = 불변) | Maven Central / coursier | coursier 108 MiB + sbt-boot 74 MiB | 없음 |
| cocotb + python 3.13 | 버전 좌표 (python 은 **마이너**) | PyPI / uv | 125 MiB | 없음 |
| sby · boolector · btor2tools · lingeling | **커밋 sha** (불변) | GitHub | 소스 클론 | 없음 |

읽는 법 두 가지를 못박는다:

- **가장 급한 것은 jar 가 아니다.** jar 는 4.3 MiB 이고 상류가 롤링이라 눈에
  띄었을 뿐이다. **분량으로도 위험으로도 큰 것은 ALA 층**이다 — 2.6 GiB 이고,
  더구나 이 축에서 유일하게 *내용 고정조차 없는* 층이다. ALA 가 옛 스냅샷을
  지우면 해시 대조가 실패하는 게 아니라 **무엇이 없어졌는지도 모른다.**
- **불변 좌표인 층은 보관 우선순위가 낮다.** 커밋 sha 로 묶인 넷과 Maven 릴리스는
  상류가 지우지 않는 한 다시 받을 수 있고, 그 「지우지 않는 한」이 정본이 말한
  「어느 핀도 사지 못하는 보장」이다. 낮은 것이지 없는 것이 아니다.

### ⚠️ 재지 않은 것

- ALA 의 스냅샷 보존(purge) 정책 — **재지 않았다.** 2026/08/12 스냅샷을 몇 년
  뒤에도 받을 수 있는지 모른다. 이 표의 위험 순위는 그 미측정 위에 서 있다.
- ALA 패키지의 **압축 다운로드** 총량 — 재지 않았다. 위 2,596 MiB 는 *설치 후*
  크기이고 보관에 필요한 것은 `.pkg.tar.zst` 총합이다(대체로 더 작다).
- Maven Central / PyPI / GitHub 의 아티팩트 보존 정책 — 재지 않았다.
- Docker Hub 의 옛 다이제스트 보존 정책 — 재지 않았다 (base 판정과 연동).

## 3. 거처 선택지와 대가

### 결정 (2026-09-11) — ⒜ 저장소 안, **jar 하나만**; ALA 층은 열린 채

사용자 판정 축자: **「landing -> commit -> 대기」**. 앞서 사용자가 「캐시까지
재현할 필요는 과연 있을까?」로 ALA 층 보관을 물었고, 권고(jar 만; ALA 는 보존이
목적인 아카이브라 다른 결손)에 이 판정으로 답했다. ALA 층은 **이 파도의 범위
밖**이다 — §2 의 「가장 급한 것은 jar 가 아니다」는 그대로 참이고, 아래 §6 이
그것을 미결로 계속 든다.

- **착지 실물**: `.devcontainer/vendor/tla2tools.jar` (4,490,846 B, b2
  `a2ccfb8c…`, 상류 자산과 바이트 동일 — 2026-09-11 다시 받아 대조) ·
  `vendor/README.md`(번들 구성 실측) · `vendor/licenses/`(라이선스 본문 13) ·
  루트 `LICENSE.md` §7 · 루트 `NOTICE` 의 「Third-party content redistributed
  verbatim」 절. Dockerfile §3 은 `curl` 을 지우고 `COPY` + `b2sum -c`.
- **착지 당일 확증 결함 넷(수리 완료, 같은 파도)**: ① 루트 `NOTICE` 가 tracked
  로 있었는데(`4d80c76`, 2,179 B) 실장 보고가 「없음」이라 적었고, 그 25행
  「not redistributed here」가 착지로 거짓이 됐는데 안 고쳐졌다 → 예외 절
  신설. ② `vendor/README.md` 의 「실측」표가 128-hex 해시 전문·크기·build/rev
  를 담은 **셋째 사본**(lint 정의역 밖, 재핀 절차 어디도 갱신을 말하지 않음)
  → 값을 지우고 선언처를 가리키게; lint 가 그 파일에서 128-hex ·
  `YYYY.MM.DD.HHMMSS` 꼴을 **금지**(V4·V5, 변이 26→28). CI build-arg 축과
  같은 판정 — 대조가 아니라 금지. ③ 번들표 「엔트리」 유도 설명이 거짓
  (`awk -F/ … uniq -c` 는 최상위 합만 낸다) + 셀 셋이 상위 접두로 세어져
  있었다(53→52 · 19→18 · 90→89) → 행마다 `grep -c '^<접두>'` 로 통일하고
  최상위 합 대조를 적음. ④ 루트 `module-info.class` 가 `com.sun.mail.smtp
  1.6.8` 의 것인데 「최상위 파일 5」로만 세어 귀속이 비어 있었다 → javamail
  행에 귀속. 교훈은 하나다 — **재지 않은 것을 쟀다고 적으면 그 문장이 다음
  결함의 씨앗이다**(①·③ 둘 다 그 형태).
- **보관본은 선언이 아니라 내용이다.** 선언처는 여전히 둘(Dockerfile ·
  devcontainer.json)이고, `lint_toolchain_pins.py` 가 보관 jar 의 blake2b ==
  `TLA_BLAKE2B512` 를 잰다(`--self-test` V1 훼손 · V2 핀만 갱신 · V3 부재).
- **대가(감수)**: git 에 4.3 MiB 바이너리. 재핀마다 사본이 이력에 영구히 쌓인다 —
  다만 재핀은 이제 **선택**이지 강제 수리가 아니므로 빈도는 이쪽이 정한다.
  **LFS 는 쓰지 않는다** — ⒝ 의 대가 그대로: LFS 서버가 새 상류이고, clone
  하나로 환경을 다시 지을 수 있어야 한다는 ⒜ 의 전제와 어긋난다.
- §3 「종합」의 앞선 질문 둘에 대한 답: ① 재현의 단위는 **저장소**(⒜). ② 보관
  대상은 **jar 층까지** — 축 전체가 아니다. 그래서 정본 §6.6.2 의 충분조건은
  여전히 축 전체에서 미달이고, 정본 `:606` 을 그렇게 고쳤다.
- **재핀 절차의 변화**: 상류 → 보관본 교체 → 핀 넷 갱신(둘) → `make rtl-pins`
  → `--no-cache` 빌드 + 스모크 → 374 run. 상류 표류는 수리 사건이 아니다.

저장소 규율은 「전 참조를 내용으로 고정」이다. 각 선택지가 그것과 어떻게 만나는지
함께 적는다.

### (a) 저장소 안에 직접 커밋

- **분량**: jar 만이면 4.3 MiB. **ALA 층까지면 GiB 급 — 성립하지 않는다.**
- **대가**: git 이력은 지워지지 않는다. 재핀할 때마다 새 사본이 영구히 쌓이고,
  이 축은 상류가 롤링이라 **재핀이 반복 이벤트**다(8/11 → 8/21, 열흘 간격 관측).
  clone 비용이 단조 증가하고 되돌릴 수 없다.
- **규율 정합**: 가장 높다. 참조가 아니라 내용 자체가 저장소에 든다.
- **판정 재료**: jar 한 층에는 성립하나 **축 전체에는 성립하지 않는다.** 이
  선택지를 고르면 「어느 층을 보관하고 어느 층은 포기하는가」를 함께 정해야 하고,
  그 부분 보관은 정본이 말한 *충분조건*을 축 전체로는 여전히 만족하지 못한다.

### (b) git-lfs

- **분량**: 대용량을 감당한다. ALA 층도 원리상 가능.
- **대가**: **의존이 하나 늘고, 그 의존이 곧 새로운 상류다.** LFS 서버가 사라지면
  포인터만 남는다 — 지금 겪는 문제와 *같은 모양*이 한 겹 안쪽으로 옮겨갈 뿐이다.
  clone 에 lfs 설치가 전제되어 재현의 진입 장벽이 올라간다.
- **규율 정합**: 중간. 내용 주소화는 유지되나 내용의 *거처*는 여전히 남의 것이다.
- **판정 재료**: 「보관」이 아니라 「다른 데 맡김」이라는 지적을 받을 수 있다.
  자체 호스팅 LFS 이면 (d) 에 가까워진다.

### (c) 별도 아티팩트 캐시 (저장소 밖, 이쪽이 소유)

- **분량**: 제한 없음. ALA 층을 포함한 축 전체를 담을 수 있는 **유일한 선택지**.
- **대가**: 저장소만으로는 재현이 닫히지 않는다 — clone 한 사람이 캐시에 닿지
  못하면 처음과 같다. 캐시의 백업·수명·접근이 **새 운영 부담**으로 선다.
  「어디에 두는가」가 「누가 유지하는가」를 부른다.
- **규율 정합**: 내용 고정은 그대로 두고 가용성만 이쪽으로 가져온다. 규율을
  깨지 않으나 저장소 경계 밖에 조건을 하나 만든다.
- **판정 재료**: 축 전체를 덮을 수 있다는 점이 결정적이다. 대신 「저장소가
  재현의 단위인가」라는 더 앞선 질문에 답해야 한다.

### (d) 상류 미러 다중화

- **분량**: 보관하지 않으므로 0.
- **대가**: **충분조건을 만족하지 못한다.** 정본이 「상류가 계속 준다는 보장은
  어느 핀도 사지 못한다」고 적은 그 자리에 상류를 더 놓는 것이다. 미러가 n 개면
  전부 사라질 확률이 낮아질 뿐 0 이 되지 않는다. 게다가 TLA+ 층에는 애초에
  **미러가 없다** — 2026-08-29 실측이 Maven 경로를 기각했고(얇은 jar 로는 374 run
  전량 실패), 그것이 유일한 대안 경로였다.
- **규율 정합**: 필요조건만 유지. 충분조건은 여전히 미달.
- **판정 재료**: 단독으로는 답이 아니다. 다른 선택지의 **보조**로만 뜻이 있다.

### 같은 축에 새로 붙은 것 — Rust 툴체인 (2026-08-30)

사용자 방침이 「모든 Rust 코드들은 2024 Edition, stable toolchain version
>= 1.97」을 선언했다. **하한 선언과 이 축(내용 고정 vs 좌표)이 만나는 자리**이고,
실측은 [`dev_platform_axis.md`](./dev_platform_axis.md) §3.1 에 있다 — 요지만:
하한에는 §2 가 `ALA_SNAPSHOT` 에 대해 말한 *좌표*조차 없다. 값도 판정도 여기
넣지 않는다.

### 종합 — 결정에 필요한 앞선 질문

선택지를 고르기 전에 답해야 하는 것이 둘 있고, **둘 다 이 파도가 답하지 않는다:**

1. **재현의 단위가 저장소인가, 저장소+캐시인가.** (a)/(b) 는 전자를, (c) 는
   후자를 전제한다. 이건 취향이 아니라 「clone 하나로 환경을 다시 지을 수
   있어야 하는가」라는 정책이다.
2. **보관 대상이 어느 층까지인가.** jar 만이면 (a) 가 즉시 성립한다. 정본이
   이름한 대로 축 전체면 (c) 밖에 없다. 위 표의 「가장 급한 것은 jar 가 아니다」가
   이 질문을 피할 수 없게 만든다.

  - 한쪽 선언뿐: `COCOTB_PYTHON` · `SBY_COMMIT` → devcontainer.json 에 신설.
  - **양쪽에 있는데 대조 밖**: `ALA_SNAPSHOT` · `COCOTB_VERSION` · `WITH_SBY` ·
    `WITH_BTORMC` → 등재. 이 중 `ALA_SNAPSHOT` 이 **이 파일에서 가장 무거운
    핀**인데 가장 오래 대조 밖에 있었다.
  - 대조 대상이 아닌 것과 그 이유: `UID`/`GID`(호스트 적응 — 문자열 대조 불성립),
    `USERNAME`(신원 값, 어긋나면 조용하지 않고 즉시 죽는다) → `ARGS_NOT_COMPARED`.
  - **구조**: 등재 완전성 검사 신설. 새 ARG 는 어느 표에도 없으면 lint 가 죽는다.
    목록을 늘린 것이 아니라 **누락이 실패가 되게** 한 것이 요지다 — 손으로
    유지하던 등재가 넷이나 뒤처져 있었던 것이 이 검사가 필요한 이유다.
  - 거꾸로 방향도 신설: devcontainer.json 이 Dockerfile 에 없는 인자를 넘기면
    빌드가 **조용히 무시**하는데 신호가 없었다. 오타 하나로 핀이 무력화된다.
- **base 이미지 판정** — 아래 §5.

## 4b. 그 파도의 전수 검증이 되잡은 것 (같은 날, 뒤이어)

위 §4 를 만든 파도 자신이 **정의역을 잘못 그었고**, 그 잘못이 하나는 blocker 였다.
여기 적는 이유는 교훈의 모양이 이 문서의 주제와 같기 때문이다 — *손으로 그은
정의역은 반드시 뒤처진다*.

### (1) 넷째 선언처 — CI (blocker, 실제로 CI 를 죽이고 있었다)

`.github/workflows/gates.yml:100-110` 이 같은 핀 **여덟**을 `--build-arg` 로
넘기고 있었다. `--build-arg` 는 ARG 기본값을 **덮으므로** 그것은 「참고용 사본」이
아니라 셋 중 **가장 센 선언**이었다. 그런데 —

- 2026-08-29 의 재핀 커밋 `cdc769d` 는 이 파일을 건드리지 않았다
  (`git show --stat cdc769d` · `git log -- .github/workflows/gates.yml` 둘 다 확인).
- 그래서 CI 는 죽은 해시 `4b2313f3…` 를 계속 넘기고 있었다. 상류를 이 세션에서
  다시 받아 실측: **4,487,757 B / b2 `644f4331…`** ⇒ Dockerfile §3 의
  `curl … | b2sum -c -` 가 그 인자로는 **반드시 죽는다.**
- 가려져 있던 이유: `cache-from: type=gha` 가 그 RUN 층을 재사용했다. 그리고
  같은 파도가 `FROM archlinux:base-devel` → `docker.io/library/…` 로 바꿨으므로
  **다음 CI 실행부터는 캐시가 무효화돼 그 실패가 드러난다.** 즉 base 완전 수식이
  이 결함을 만든 것이 아니라 **가리개를 걷었다.**

**처분 — 「대조 추가」가 아니라 「금지」.** 근거:

- CI 는 이 저장소의 Dockerfile 을 그대로 빌드한다. 넘기지 않은 ARG 는 그 파일의
  기본값이 된다 ⇒ 사본이 **정보를 하나도 더하지 않는다.** 실제로 지운 여덟 중
  일곱은 기본값과 글자 그대로 같았고, 중복의 유일한 효과가 이 사고였다.
- devcontainer.json 은 다르다 — VS Code 가 Dockerfile 을 읽기 **전에** 인자를
  정하는 별개 소비자라 사본이 필요하다. 그래서 저쪽은 *대조*, 이쪽은 *금지*다.
- 대조로 두면 사람이 세 곳을 맞춰야 하고, **뒤처지는 것이 바로 그 구조**다.
  이 사고 자체가 그 구조의 출력이다.

남긴 것: `UID`/`GID` 둘 (러너 사용자 1001 — bind mount 소유자가 어긋나면 뒤
step 의 `git diff --exit-code` 가 권한으로 깨진다). 재현성 축이 아니다.

기계: lint 가 `.github/workflows/` 를 **rglob 순회**한다 — 손 목록이 아니므로
새 워크플로도 자동으로 든다. `build-args:` 블록과 `run:` 안의 `--build-arg`
둘 다 본다. 워크플로가 0 이면 통과가 아니라 실패다(「덮었다」와 「잴 것이
없었다」를 구분한다).

### (2) ARG 완전성 검사가 합법 표기 넷으로 우회됐다

같은 파도가 세운 「미등재 ARG 는 실패한다」가 **성립하지 않는 표기가 넷** 있었다.
옛 검사는 `re.match(r"^\s*ARG\s+([A-Z_][A-Z0-9_]*)", line)` 한 줄이었다.

실측(`podman build --no-cache`, archlinux:base-devel 위)으로 넷이 전부 유효한
Dockerfile 임을 확인했다 —

| 표기 | podman 결과 | 옛 lint |
|---|---|---|
| `ARG AAA=1 BBB=2` | `AAA=1 BBB=2` | `BBB` 안 보임 → **rc=0** |
| `arg CCC=3` (소문자 명령) | `CCC=3` | **rc=0** |
| `ARG ddd=4` (소문자 이름) | `ddd=4` | **rc=0** |
| `ARG EEE=5 \` + `FFF=6` (줄 이음) | `EEE=5 FFF=6` | 둘째 이름 안 보임 → **rc=0** |

(넷째는 브리프에 없던 것으로, 이 세션이 추가로 재서 찾았다. `ARG XX=1 # note`
도 podman 이 받아들여 `XX=1` 을 선언한다 — 그것도 파서에 넣었다.)

처분: 정규식을 파서로 바꿨다 — 줄 이음 접합 → 대소문자 무시 `ARG` → 공백
분해로 `이름[=값]` 토큰 전수. 그리고 **읽지 못한 토큰은 버리지 않고 실패시킨다**
(조용히 버리는 것이 애초의 결함이므로). 「이름은 있는데 기본값이 없다」와
「이름이 아예 없다」도 이제 다른 말로 적힌다 — 옛 파서는 둘을 뭉갰다.

### 음성 시험 (2026-08-30, 최종 코드에 15종 전부 실행)

| # | 넣은 것 | rc |
|---|---|---|
| N0 | 무개변 (대조군) | **0** |
| N1 | 한 줄 다중 ARG 의 둘째 이름 미등재 | 1 |
| N2 | 소문자 ARG 이름 미등재 | 1 |
| N3 | 소문자 `arg` 명령 미등재 | 1 |
| N4 | 줄 이음 둘째 이름 미등재 | 1 |
| N5 | 꼬리 주석(`# note`) 뒤 미등재 | 1 |
| N6 | 기본값 없는 `ARG BARE_UNREGISTERED` | 1 |
| N7 | 등재 핀의 devcontainer.json 값 어긋남 | 1 |
| N8 | devcontainer.json 한쪽 선언 삭제 | 1 |
| N9 | 등재 핀의 **기본값만** 제거 (이름은 남김) | 1 |
| C1 | gates.yml 에 죽은 TLA 해시 **복원** | 1 |
| C2 | gates.yml 에 **값이 맞는** 핀 재선언 | 1 |
| C3 | `run:` 스텝의 `--build-arg SBT_VERSION=…` | 1 |
| C4 | **새 워크플로 파일**에 핀 (정의역 순회 확인) | 1 |
| C5 | 허용 키 오타로 허공 build-arg | 1 |

N1–N6 은 **고치기 전에는 N1·N2·N3·N4 가 rc=0 이었다** — 즉 이 표는 「검사가
있다」가 아니라 「검사가 문다」를 인쇄한다. N9 는 옛 판이 「없다」로 뭉개던
자리로, 이제 다른 말로 실패한다.

C2 가 이 축의 요지다 — **값이 맞아도 실패시킨다.** 사본을 허용하면 다음 재핀이
같은 자리에 같은 사고를 다시 놓는다.

### 실물 확인 — 「CI 가 이제 무엇으로 빌드하는가」를 재서 답한다

핀 사본을 지웠으므로 CI 는 **Dockerfile ARG 기본값**으로 빌드한다. 그것이
실제로 서는지 재지 않고 적으면 이 문서가 금지하는 짓을 하는 것이다. 그래서
`--build-arg` 없이(= CI 와 같은 조건, UID/GID 만 다름) from-scratch 로 지었다:

    podman build --no-cache --pull -t wt-pin-1 .devcontainer   → rc=0, 35/35 스텝

- STEP 9 — `/usr/share/java/tla2tools.jar: OK` ·
  `[wt] TLC 스모크 OK — 2026.08.21.155922 (rev: 9787e65) / b2 644f4331…`
  ⇒ **CI 가 넘기던 죽은 해시로는 반드시 죽던 그 층이, 기본값으로는 산다.**
- `[wt] SpinalHDL 스모크 OK` · `[wt] sby OK @ f57802a1…` ·
  `[wt] btormc 3.2.4 OK @ 393cdfba…`
- 자기보고(`~/wt-toolversions.sh`): verilator 5.050 · iverilog 13.0 · yosys 0.66 ·
  cocotb 2.0.1 · z3 4.16.0 · TLC 2026.08.21.155922 · tla2tools b2 `644f4331…` ·
  sby v0.66 · btormc 3.2.4 · java 21.0.12 · sbt 1.12.15 · scala 2.13.12 ·
  SpinalHDL 1.14.2 — **전부 핀과 일치.**

⚠️ 재지 **않은** 것: 이 이미지로 `make rtl-formal`·`proofs/tla/run.sh` 를 다시
돌리지 않았다. 2026-08-29 에 같은 핀 집합으로 358/358 · 16/16 을 쟀고 그 뒤
핀 값이 하나도 바뀌지 않았으므로(이 파도는 *사본*을 지웠지 값을 안 건드렸다)
다시 재지 않았다 — 그러나 그것은 추론이지 측정이 아니다.
그리고 **GitHub 러너에서 도는 것은 재지 않았다.** 여기서 잰 것은 podman /
이 호스트다. GHA 는 buildx(BuildKit)이고 `cache-from: type=gha` 가 붙는다.

## 5. base 이미지 — 판정과 그 근거

`FROM archlinux:base-devel` → `FROM docker.io/library/archlinux:base-devel`.
**완전 수식은 했고 다이제스트는 박지 않았다.** 둘은 별개 판단이다. 전문은
Dockerfile §0 주석에 있고 요지만 옮긴다:

- **완전 수식은 했다.** 짧은 이름의 해석은 저장소가 아니라 호스트 설정이 정한다.
  이 호스트에서 실제로 갈라져 있었다 — 별칭표는 `docker.io/library/archlinux` 를
  선언하는데, 로컬에 있던 것은 `docker.io/archlinux/archlinux:base-devel`
  (**다른 저장소**) 하나뿐이었고, 22시간 전 빌드된 `wavetensor-dev:scala` 의
  바닥 층이 **그것과 일치**한다(`ae7749e3…`). 게다가 그 base 는 2026-05-08 자로
  3.7개월 묵었다 — `--no-cache` 로 구웠는데도. (`--no-cache` 는 층 캐시를 끄지
  `--pull` 을 켜지 않는다.)
- **다이제스트는 박지 않았다.** 흔한 반론(「보안 갱신이 멈춘다」)은 실측으로
  **성립하지 않는다**: 3.7개월 떨어진 두 base 위에 ALA 단계만 얹어 대조하니
  `pacman -Q` 170 패키지가 **완전히 동일**하고 `/usr` 아래 전 파일 sha256 이
  **차이 0건**이었다. base 는 도구 바이트에 0 기여한다. 보안 통화성을 쥔 것은
  base 가 아니라 `ALA_SNAPSHOT` 이다.
  박지 않는 진짜 이유는 다르다 — **보관본 없는 핀을 하나 더 만드는 일**이고,
  그것이 §3 이 TLA+ 에서 겪고 있는 결손 그 자체다. 기여 0 인 층을 고정해서 얻는
  것보다 크다. ⇒ **위 §3 의 거처 결정이 나면 다시 연다.** 조건부 판정이다.
  (2026-09-11: §3 의 결정은 jar 층에 한정된 ⒜ 다. base 는 jar 가 아니라 ALA
  층 쪽 질문이고 그쪽은 열린 채이므로 **이 판정은 다시 열지 않았다** — base
  다이제스트를 박으면 다시 보관본 없는 핀이다.)

### 재지 않은 것

- base 차이로 남은 것 셋: `gconv-modules.cache` · `udev/hwdb.bin` ·
  `systemd/catalog/database` (구 base 에만 존재). 파생 색인이라 도구 버전이
  아니라고 판단했으나, **그 판단이 옳은지는 재지 않았다** — 이것들이 어떤
  게이트에도 영향을 주지 않는다는 것을 증명하지는 않았다.
- Docker Hub 다이제스트 보존 정책 — 재지 않았다. 위 판정은 그 보존을 신뢰하지
  않는 쪽이라 이 미측정에 기대지 않지만, **반대 판정을 하려면 이것부터 재야 한다.**

## 6. 남은 결손 (이 파도가 닫지 않은 것)

1. **보관본 — jar 층은 착지(2026-09-11, §3 「결정」). ALA 층은 미결.** 정본
   `:606` 이 「한 층에만 섰다」로 바뀌었고 충분조건은 축 전체로는 여전히 미달.
2. **ALA 층의 내용 고정 부재.** 날짜 좌표뿐이고 해시가 없다. 보관본과 별개의
   결손이며(정본이 「필요조건조차 층별로 갈린다」로 적은 것이 이 자리),
   보관을 안 하더라도 *해시 목록만이라도* 뜨는 것은 별도로 가능한 처분이다 —
   이 파도는 하지 않았다.
3. **핀 lint 의 음성 시험이 상주하지 않는다 — 이제 이것이 가장 큰 잔여다.**
   2026-08-30 에 13종(§4b)으로 물리는 것을 확인했으나 **전부 일회성 실행이고
   저장소에 남지 않았다.** 이 결손의 값은 같은 날 실증됐다: 앞선 파도가 세운
   완전성 검사가 합법 표기 넷으로 우회됐고, 그것을 잡은 것은 상주 시험이
   아니라 사람의 전수 검증이었다. 이 저장소가 `yosys bind 묵살`·`sby 합성
   태스크 회귀`에서 배운 교훈이 정확히 이것이다 — **검사가 무는지를 기계가
   재야 한다.** 다음 파도의 1순위.
   ⚠️ 그리고 §4b 의 두 결함이 보인 것은 더 나쁜 쪽이다: 「검사를 세웠다」가
   「검사가 문다」를 뜻하지 않았다. 새 검사를 세울 때마다 음성 시험을 함께
   두지 않으면 같은 일이 반복된다.
4. **산문 사본은 여전히 정의역 밖이다.** §4b 가 닫은 것은 *빌드에 넘어가는*
   사본(build-arg)이다. 값만 적어 둔 산문은 그대로다 — 실측으로 세어 확인:
   `rtl/README.md`(표 6행) · `.devcontainer/README.md` · `rtl/sim/README.md:39`
   (cocotb 2.0.1). 이것들은 `--build-arg` 가 아니므로 docstring 이 (b) 라 부른
   *조용히 다른 버전으로 재는* 실패를 만들지 못한다 — 그래서 급이 낮다.
   그러나 낡으면 사람이 잘못 읽는다. **처분 미정**이고, 판정에 필요한 앞선
   질문은 「산문 안의 버전 문자열을 기계가 대조할 수 있는 형태로 표시할
   것인가」다(그 표시 규약 자체가 별개의 결정이다).
5. **`COCOTB_PYTHON` 은 등재됐으나 여전히 마이너 좌표다.** 두 선언의 일치는 이제
   기계가 재지만, `3.13` 이 빌드 시점에 어느 패치로 풀리는지는 고정되지 않는다
   (실측 2026-08-29: `3.13.15`). 등재는 *대조*를 세운 것이지 *고정*을 세운 것이
   아니다 — 둘을 섞어 읽지 말 것.
