# opcode 12비트 확장 — 제안과 실측 평가

> ### 📌 지위 — 사용자 제안(2026-08-28) + 실측 평가. **채택은 아직 결정되지 않았다.**
>
> 정본은 `docs/wt64v1-architecture-guide/` 하나이고 이 문서의 어떤 문장도
> 계약이 아니다.

## 1. 제안 원문 (2026-08-28)

> opcode 의 자릿수를 늘릴 필요가 있어 보이는데, **#22 까지의 opcode 들은 앞에
> 0x0 을 하나 붙이는 걸로 일괄 처리**(즉, `0x60` → `0x060`)하고, **맨 앞
> 니블에 따라 영역을 나누는** 건 어떨까? `0x0##`~`0x3##` 영역은 기존 opcode
> 공간의 크기를 단순히 키운 것으로 간주하고, `0x4##`~`0x7##` 영역은 #24
> (신규 확장)를 위한 opcode 공간으로 활용하며, 나머지 영역은 예비용으로
> 남겨두는 식으로.

제안 시점의 상정: **공짜로 붙이기는 어려울 것** — 즉 재인코딩 비용을 각오했다.

## 2. 실측 — 바이너리 층에서는 공짜다. 그리고 그것은 우연이 아니다

기본 헤더 32b 실측 (`01-isa-asm.typ` §1.3.1 표):

```
[31:24] opcode 8b · [23:20] next_hdr 4b · [19:16] flags 4b
[15:8]  reserved 8b — **반드시 0. 0 이 아니면 malformation**
[7:0]   bh_len 8b
```

세 층이 전부 실물로 확인됐다:

- **어셈블러**가 `[15:8]` 에 0 을 방출한다 (`wavetensor_asm.py:2041` —
  `(opcode & 0xFF) << 24`, 예약 자리는 조립식에 아예 없어 0).
- **재구현 RTL** 이 비0 을 판정한다 (`DecodeWalk.scala:223,262` —
  `resvFld = iInstr(0)(15 downto 8)`, `resvBad = resvFld =/= 0` → malformed).
- **방출면**이 그 비트를 0 으로 지워 내보낸다 (`:285` — SEC-7 (ii)).

⇒ **기존의 모든 적법 바이너리는 이미 확장 니블 자리에 0 을 갖고 있다.**
`0x060 == 0x60` 은 수치로도 동일하다 — 재인코딩할 것이 **한 비트도 없다.**
`truth_table_premigration.json` 벡터들도 재캡처 불요다(예약 비트가 이미 0).

**이것이 공짜인 이유는 §5.7 엄격 규율의 배당금이다.** 정본이 명령 인코딩
예약을 「비0 = malformation」으로 못박은 목적이 정확히 이것 — *나중에 그
자리를 claim 할 때 쓰레기를 재해석하지 않기 위해서*다. MMIO 식 관대 예약
(쓰기 무시·읽기 0)이었다면 옛 바이너리에 아무 값이나 있을 수 있어 이 확장은
공짜가 아니었다. **상정("공짜는 어렵다")은 관대 예약 세계에서는 옳았다.**

## 3. 공짜가 아닌 곳 — 검증층. 전수 목록

바이너리는 안 움직이지만 **그 비트를 보는 모든 검사가 움직인다**:

| # | 자리 | 무엇이 바뀌나 |
|---|---|---|
| 1 | 정본 §1.3.1 표 | `[15:8] reserved 8b` → `[15:12] reserved 4b` + `[11:8] opcode_ext 4b` (배치는 §4). opcode 표기 전반 `0x##` → `0x0##` |
| 2 | `DecodeWalk.scala` | `resvFld` 폭 8→4 · `masked` 범위 · opcode 결선 `{ext, [31:24]}` 12b |
| 3 | **GUARD-MAP 4건** — `Decode.resv_judged / resv_not_indexed / resv_not_timed / resv_not_echoed` | 문면의 `[15:8]` 이 전부 좁아진다. TLA cfg ~10 run (`Decode_del_resv_*` 3형상 × 3가드 + pair) · SVA 하네스(`DecodeWalk_props.sv:203` 등) · **증거 재측정** (sby 해당 태스크 — 「모듈 태스크만 돌리면 합성 증명이 조용히 깨진다」 함정의 사정권) |
| 4 | **SEC-7 (ii) 논증 재유도** | `resv_not_echoed` 의 「`oInstr_0[15:8] == 0` 상시」가 깨진다 — **`[11:8]` 은 이제 opcode 라 방출되어야 한다.** 마스킹은 `[15:12]` 로 좁아지고, 「같은 판정을 받은 두 명령은 방출면에서 구별 불가능」 논증에서 opcode_ext 는 (opcode 가 이미 그렇듯) 구별 인자로 *정당하게* 남는다 |
| 5 | ⚠️ **fp ROM 게이트 — 공허 PASS 함정** | `in_fp_block = (opcode[7:4] == 0x7)` 이 **ext 니블 == 0x0 을 함께 봐야 한다.** 안 보면 `0x47B`·`0x87B` 가 `0x07B` 의 ROM 행에 얹힌다 — Di 확정안이 `0x80` 에서 문서화한 것과 같은 결이다 |
| 6 | 어셈블러 | opcode 인자 12b 수용 · legality 의 예약 검사 협소화 · ISA JSON `code` 는 수치 그대로(>0xFF 는 신규만) |
| 7 | **미지 opcode·영역 처분 규범 신설** | 현행 정본에 「미지 *opcode*」의 일반 처분 문면이 그립다(미지 EH 는 malformation 명문). 4096 칸이 열리면 이것이 필수가 된다 — 영역별: 미배정 값 = malformation · 예비 영역(`0x8##`+) 전체 = malformation (claim 전까지) |

**전부 유한하고 열거 가능하다.** pre-stable 이므로 recapture 는 정규
이벤트(`prestable_compat_policy`)이고, 지금이 이 확장이 가장 싼 시점이다 —
stable 후에는 §5.7 동결이 이것을 사실상 막는다.

## 4. 배치 권고 — 확장 니블은 `[11:8]`

두 후보 중 `[11:8]` 을 권고한다:

- `[11:8]` = opcode_ext ⇒ **남는 예약 `[15:12]` 가 flags `[19:16]` 에 인접** —
  미래에 플래그가 자라면 연속 구간으로 자란다.
- `[15:12]` = opcode_ext 면 남는 예약이 flags 와 opcode_ext 사이에 끼인다.

opcode 가 `[31:24]`+`[11:8]` 로 물리적으로 갈라지는 것은 디코드에서 결선
하나다. INV-T2 의 「고정 니블 분할 금지」는 *목적지 명명에 arity 를 싣는 것*의
금지이지 필드의 물리 연속성 요구가 아니다.

## 5. 영역 구획 평가

| 영역 | 용도 (제안) | 평가 |
|---|---|---|
| `0x0##`–`0x3##` | 기존 공간의 단순 확대 (base + Di/Lf/C 계보) | 1024칸. base 256 + Di(`0x07B`·`0x080`) + C 재배정 + Lf 가 넉넉히 든다 |
| `0x4##`–`0x7##` | #24 신규 확장 (Txtsmp · Ctrl 등) | 1024칸. **이종 PE 도달 경로와 자연 정합** — B.5 미결 「유닛 도달 경로의 규범 부재」(술어가 측정 트랙에만)의 답 후보: 영역 니블 → 유닛 *부류* 술어. 단 **분류이지 라우팅이 아니다** — 배달은 여전히 LNID 사상표가 한다 (「라우터를 짓지 말 것」) |
| `0x8##`–`0xF##` | 예비 | 2048칸. claim 전까지 전역 malformation (§5.7 엄격의 opcode 판) |

주의 하나: 영역 경계는 **관례이지 하드웨어 판정이면 안 되는 축이 있다** —
「`0x4##` 는 신규 확장」이라는 사실 자체를 디코더가 알 필요는 없다(미배정 =
malformation 으로 족하다). 하드웨어가 아는 것은 배정된 opcode 뿐이고, 영역은
*배정 절차의 규범*(어느 확장이 어디서 번호를 받는가)이다. 이 구분을 명세에
적지 않으면 영역 니블이 슬그머니 dispatch 비트가 된다.

## 6. 파이프라인 영향

- **Di 명세(#22, 진행 중)**: 표기만 `0x7B`→`0x07B`, `0x80`→`0x080`. 수치
  동일이므로 커밋 때 일괄 갱신으로 족하다.
- **C 재배정(#23)**: 8b 공간의 「빈칸 여섯」 제약이 풀린다 — `0x0##` 안에서
  깨끗한 연속 블록을 받을 수 있다.
- **#24**: `0x4##`–`0x7##` 가 처음부터 열린 채 시작한다.

## 7. 미결 — 사용자 결정 대기

1. **채택 여부** — 이 문서는 평가이지 결정이 아니다.
2. 확장 니블 자리 `[11:8]` (권고) vs `[15:12]`.
3. 미지 opcode 처분의 정확한 문면 — malformation 으로 통일할지, 능력 부재
   갈래를 남길지 (§1.6.2 배타성 축).
4. 영역 규범의 거처 — base 정본 §1.3 인가, `docs/extensions/` 총론인가.
