# WT64v1 RTL 전면 재구현

## 정본은 하나다

**`docs/wt64v1-architecture-guide/main.pdf` 가 유일한 정본이다.**

이 저장소의 다른 문서 — `.claude-memos/wt64v1_spec.md`, `claude.md`,
`.claude-memos/` 전반 — 은 **비정본**이다. 그 문서들과 정본이 어긋나는 지점은
정본의 **부록 B 가 정정본**이며, 재구현은 부록 B 를 먼저 읽는다.

## clean-room 경계 — 무엇을 읽고 무엇을 읽지 않는가

재구현이 clean-room 으로 성립하려면 재구현 쪽이 원본 구현 표현에 노출되지
않아야 한다. 이것은 형식적 예방이 아니다 — 구현 표현이 섞이면 "무엇을
만들어야 하는가" 대신 "원본은 어떻게 했는가"를 읽게 되고, 그 순간 독립 구현
이라는 주장이 무너진다.

| | 대상 | 근거 |
|---|---|---|
| ✅ **읽는다** | `docs/wt64v1-architecture-guide/**` | 정본 |
| ✅ | `asm/wavetensor_asm.py` | 어셈블러 오라클. 서문이 *"clean-room 오염이 아니다 — 어셈블러는 RTL 이 아니다"* 라고 명시 |
| ✅ | `scripts/golden_*.py` | golden 모델 — 산술 의미론의 authority |
| ✅ | `isa/wt64v1_isa.json` | 정본 §1.7.3 이 요구하는 "기계가 읽는 단일 정의"의 실물 |
| ✅ | `include/generated/*.hex` | golden 이 낸 기대값 벡터 |
| ⚠️ | `isa/truth_table_encwave.json` | **오라클로만** (현행 인코딩). 인코딩 개정 파도 W1~W8 반영 RTL 에서 전량 재캡처한 domain_version 4 · 5,934점 + 확장 니블 탐침 207점. 통과/실패를 받는 것은 안전하나 **명세로 읽으면 오염** |
| ⚠️ | `isa/truth_table_premigration.json` | **오라클로만**, 그리고 **이관 전 계보 전용**. 동결·존치이나 파도 이전 바이너리에만 답한다 — 현행 인코딩(CH 를 포함하는 `bh_len` · OPREF 의 CRC 니블)의 회귀 대조는 위 `encwave` 가 승계했다. 명세로 읽으면 오염인 것은 같다 |
| ⛔ | 저장소 루트 `*.v`, `tb_*.v` | 원본 RTL |
| ⛔ | 루트 `test_*.py` | 오라클 목록에 없다. 원본의 top-level 포트명·내부 계층 경로에 결합돼 있어 **간접 오염 경로**다 |

⛔ 항목을 피하는 대가로 하네스를 새로 쓴다. 입력 벡터는 어셈블러에서, 기대값은
golden 에서 직접 받는다.

## 혼재 경계 — 어느 파일이 생성물이고 어느 것이 수기인가

경계를 파일 단위로 선언하지 않으면 아무도 "이 줄을 고쳐도 되는가"에 답할 수
없다.

| 경로 | 성격 | 손편집 |
|---|---|---|
| `rtl/spinal/` | SpinalHDL 설계 (Scala) — **생성기** | ✅ 여기를 고친다 |
| `rtl/generated/` | SpinalHDL 산출 SystemVerilog | ⛔ **금지.** 생성기를 고치고 다시 낸다 |
| `rtl/sv/assert/` | SVA 후-formal 하네스 (수기) — 부착은 `expose` + 래퍼. **`bind` 금지** (yosys 0.66 이 조용히 버린다 → 공허 PASS) | ✅ |
| `rtl/sv/prim/` | 벤더 프리미티브 BlackBox 래퍼 (수기) | ✅ |
| `rtl/formal/tla/` | 선-formal 모델 · cfg · 러너 | ✅ |
| `rtl/formal/sby/` | 후-formal BMC / k-귀납 | ✅ |
| `rtl/sim/` | 자립형 cocotb 러너 + 하네스 | ✅ |

생성물은 **커밋한다.** 단 생성기와 **함께** 커밋한다 — 둘이 따로 움직이면
저장소 안의 SystemVerilog 가 무엇으로부터 나왔는지 답할 수 없게 된다.
생성물에는 헤더로 그 사실이 박힌다 (`rtl/spinal/.../Wt64.scala` 의 `rtlHeader`).

2026-08-30 에 CI 가 죽은 TLA 해시를 넘기고 있던 것이 이 규칙의 출처다 — 사본은
대조로 못 지킨다. 없애야 지켜진다.

### 실측 기록 — 이 고정에 이른 근거

가정이 아니라 실제로 재서 정한 값들이다.

- ALA 스냅샷 `2026/08/12` 에 **`sbt` 는 1.x 가 아니라 `1:2.0.6-1`** 이다. 그래도
  쓸 수 있는 이유는 그것이 *런처*이기 때문 — launcher jar 의 boot properties 가
  `version: ${sbt.version-read(sbt.version)[2.0.6]}` 이므로 2.0.6 은 **기본값**이고
  `project/build.properties` 가 이긴다.
- 같은 스냅샷에 **`scala`·`mill`·`coursier` 패키지는 없다.** Scala 컴파일러는
  sbt 가 coursier 로 받으므로 정상이며, **mill 경로는 닫혀 있다.**
- 무버전 `jdk-openjdk` 는 이 스냅샷에서 **26.0.2** 를 준다 (비-LTS).
  `jdk21-openjdk` (21.0.12.u8-1) 로 명시 고정했다.
- **SpinalHDL 은 Scala 3 빌드가 없다** (`spinalhdl-core_3` 부재). 2.13 계열뿐이고
  1.14.2 의 POM 이 의존하는 값이 정확히 `2.13.12` 다.

## 왜 SpinalHDL 인가 — 그리고 무엇이 규범이 아닌가

정본 서문은 *"사용할 HDL(Verilog / Chisel / 혼합)은 재구현팀의 자유다"* 라고
적는다. 즉 **SpinalHDL 은 정본이 지시한 것이 아니라 이 저장소의 선택**이다.
같은 이유로 TLC·cocotb·SymbiYosys 도 정본이 지목한 제품이 아니다 — 정본 6장은
어떤 형식 도구도 제품명으로 지목하지 않고 *성격*(유한 상태 모델 검사기 /
합성 프론트엔드 기반 유계 모델 검사 + k-귀납 / golden 대조)만 규정한다.

정본이 실제로 구속하는 것은 도구가 아니라 **순서**다 (§6.3, 구속력 있음):

> 선-formal → RTL → 후-formal. **1단을 건너뛴 모듈은 완료로 간주하지 않는다.**

## 현재 상태

**단계 0 (환경·규율·미결 결정) 진행 중.** RTL 설계는 아직 없다.

`rtl/spinal/src/main/scala/wt64/gen/ToolchainCheck.scala` 는 **설계가 아니다** —
`make rtl-gen` 이 실제로 무언가를 하는지 판정할 대상일 뿐이며, 재구현 설계가
착지하면 삭제된다. 생성할 것이 없을 때 조용히 성공하는 게이트는 정본 §6.7 이
지목한 실패형 그 자체다.

## 구성 표면 sub-word ABI 조항 (2026-08-24, 결정 B)

**구성 페이지(4 KiB) 전체에 대해 sub-word(바이트 인에이블) 쓰기는 거절 +
loud fault 다.** 적용 범위는 사상표(0x400~0xBFF)만이 아니라 구성 표면
전체다 — E.7 전이 워드·E.12 발화 워드가 같은 원자성 논증 위에 서 있다.

근거는 정본 §3.7.1 의 원자성 규범이 *전제*를 하나 빌려 쓰고 있었다는
발견이다. 「엔트리 폭 4 B = 단일 워드이므로 부분 갱신이라는 상태가
구조적으로 존재하지 않는다」는 논증은 **한 워드 쓰기가 쪼개지지 않는다**를
전제하는데, 정본은 그 전제를 어디에서도 보증한 적이 없다. RTL 은 포트에
바이트 스트로브를 두지 않아 구조로만 봉해 두고 있었고 — 그것은 곧
*문서화되지 않은 ABI 전제*였다. 호스트 버스(PCIe/AXI)는 sub-word 쓰기를
허용하므로, 명문화하지 않으면 상위 어댑터에서 read-modify-write 가 조용히
생기고 위 논증이 무너진다.

**이 저장소가 이행하는 몫**: `hiu/MmioConfig.scala` 의 MMIO 포트는 쓰기
낱알이 워드 하나이고 바이트 인에이블 입력이 아예 없다. 「sub-word 기입」
이라는 사건은 이 경계에 *도달할 수 없다* — 표현 불가능이 곧 이행이다.

**이 저장소 밖에서 지켜야 할 몫 (정직하게 적는다)**: 그러므로 거절의
이행 지점은 이 모듈이 아니라 **상위 어댑터(호스트 버스 → 이 포트 브리지)**
다. 어댑터는 구성 페이지에 대한 sub-word 쓰기 요청을 수락하지 말고 거절 +
loud fault 로 처리해야 한다. 여기에는 그 어댑터가 없으므로 이 요건은
**검사되지 않는다** — 미측정이지 통과가 아니다 (정본 §6.7 원칙 5). 어댑터가
착지하면 이 조항이 그 모듈의 후-formal 속성이 된다.

관련 결정 A (같은 회의): 엔트리 *내부* 예약 비트는 엄격(비0 = 거절 + loud
fault)이다. 아래 「모델 환류 대기」의 MmioConfig 둘째 항목(「예약 비트는
쓰기 무시(마스크 정규화 저장)·읽기 0」)은 이 결정으로 처분됐다 — 그 항목의
문면은 이제 낡았고, 현행 규범은 `hiu/MmioConfig.scala` 머리의 「엔트리
내부 예약 비트」 절이다. 통합자가 환류 목록을 갱신할 때 함께 처리할 것.

## 구성 페이지 구역 지도 — 호스트 ABI 결정 2 (2026-08-25)

E.1 이 `0xC00`–`0xFFF` 를 통째로 「예약」이라 선언한 탓에 정본이 규범으로
세운 표면 넷이 오프셋을 갖지 못하고 있었고 (E.9 마스킹 · E.12 문맥 소거 ·
§2.5 프로그램 적재 · §3.8 fault), RTL 은 그중 셋을 `0xC00` 에 **잠정** 배치
하고 「되돌린다」고 적어 두었다. 결정 2 가 4 KiB 페이지 전체를 다시 배정했고
이 파도가 그 이동을 이행했다.

배정 원칙 넷과 구역·워드 상수는 `top/Wt64Top.scala` 의 companion
`object Wt64Top` 스칼라독이 **유일한 출처**다 — 표를 두 곳에 적으면 그 자체가
드리프트 표면이므로 여기 옮겨 적지 않는다. 이 절이 소유하는 것은 *무엇이
배선됐고 무엇이 안 됐는가*뿐이다.

### 이 파도가 옮긴 것

| 옛 오프셋 | 새 오프셋 | 표면 |
|---|---|---|
| `0xC00`–`0xC1C` | `0xE80`–`0xE9C` | MASK_KEY[0..7] (E.9 1항) |
| `0xC20` | `0xEA0` | MASK_NONCE_PART |
| `0xC24`–`0xC38` | `0xEA4`–`0xEB8` | MASK_NONCE[0..5] (E.9 2항) |
| `0xC3C` | `0xEBC` | MASK_REKEY (E.9 4항) |
| `0xC40` | `0xEC0` | MASK_STATUS |
| `0xC44`–`0xC4C` | `0xF00`–`0xF08` | FP_PROG · FP_BIND · FP_STATUS (§2.5) |
| `0xC50`–`0xC5C` | `0xF40`–`0xF4C` | ABORT_TAG0..2 · ABORT_FIRE (E.12) |
| `0xC60`–`0xC64` | `0xF50`–`0xF54` | ABORT_COUNT · REASM_INCOMPLETE |

상위 디코더도 함께 좁혔다: `selCq` 는 `addr[11:8]==0x3` (256 B) 에서
`addr[11:7]==0b00110` (128 B) 로, `selLoc` (`addr[11:8]==0xC`) 은 사라지고
구역 열하나가 대신 선다. **전부 상수 접두 비교이며 범위 비교는 한 곳도
생기지 않았다** — 생성물에서 확인 가능하다 (`rtl/generated/Wt64Top.sv` 의
`assign sel*` 열한 줄 + `selUnwired` 한 줄). 둘째 파도가 `selFault` 를 미배선
목록에서 배선 목록으로 옮겼을 뿐 줄 수는 그대로다 — 구역 판정의 모양은 배선
여부와 무관하다는 사실이 여기서 보인다.

### 둘째 파도 — 완료 구역 *안쪽* + 장치 전역 fault 표면 (2026-08-25)

첫 파도는 구역 *경계*만 옮기고 `host/CompletionUnit.scala` 안쪽을 옛 배치로
남겼다 (파일 배정 밖이었고 아래 표로 정직하게 등재했다). 전수 검증이 그
어긋남을 RED 로 냈고, 이 파도가 닫았다.

| 워드 | 옛 (구역 안 오프셋) | 새 (정본 E.1.2) |
|---|---|---|
| CQ_BASE_LO / CQ_BASE_HI | 없음 | `+0x00` / `+0x04` (**미배선** — 아래) |
| CQ_SIZE | `+0x00` (RO, 엔트리 수) | `+0x08` (RW, `log2`(엔트리 수)) |
| CQ_HEAD | `+0x04` | `+0x0C` |
| CQ_TAIL | `+0x08` | `+0x10` |
| IRQ_STATUS · IRQ_MASK · IRQ_CLEAR | `+0x10` / `+0x14` / `+0x18` | `+0x20` / `+0x24` / `+0x28` |
| FAULT · FAULT_CLEAR | `+0x1C` / `+0x20` | **삭제** — `0xF80[16]` / `0xF84[16]` 로 |
| 엔트리 창 · 드레인 여섯 · CQ_OCC · ALLZERO | `+0x40`–`+0x7C` | 같음 (움직이지 않았다) |

**가장 위험했던 자리는 `+0x04` 다.** 정본은 CQ_BASE_HI(RW)이고 옛 RTL 도 RW
였는데 실물이 CQ_HEAD 였다 — 정본을 따라 만든 드라이버가 링 기저 상위 워드를
쓰면 완료 링의 *소비 색인이 조용히 덮인다.* 예약(쓰기 무시·읽기 0)이면
무해했을 자리가 유효한 RW 기입으로 상태를 망가뜨리는 형태이며, 그래서
**옛 오프셋을 비우는 것**이 이 수리의 본체다. 옛 FAULT_CLEAR(`+0x20`, WO)도
같은 부류였다 — 새 맵에서 그 자리는 IRQ_STATUS(RO)다.

`0x300`–`0x37F` 의 새 읽기 뮤스는 생성물에서 직접 확인된다
(`rtl/generated/CompletionUnit.sv` 의 `case(io_addr)`): 정의 오프셋은
`8'h08`·`0c`·`10`·`20`·`24`·`60`–`74`·`78`·`7c` 뿐이고 옛 자리
`8'h00`·`04`·`1c` 는 어느 분기에도 없다 — 읽기 0 이다.

**CQ_SIZE 재인코딩.** `+0x08` 읽기가 엔트리 수가 아니라 `log2`(엔트리 수)를
낸다 (깊이 8 → `32'h00000003`, 생성물에서 확인). 같은 워드가 다른 뜻을 갖게
되는 *의미 변경*이므로 옛 자리를 비우는 것이 특히 중요하다 — 드라이버가 옛
값 8 을 새 인코딩으로 읽으면 2^8 엔트리 링이라 오해한다.

**장치 전역 fault 표면 `0xF80`–`0xF90` 배선.** (착지 당시 열여덟 축. `[18]` 은
호스트 ABI 결정 4·5 파도에서 E.5.4 가 신설했고 아래 수치는 그것을 반영한 것이다 —
`Fault.N_BITS` 가 값의 단일 출처다.) 원천을 갖는 축은 전부 이미 합성
가능한 sticky 비트로 존재했고 (§3.8 만족), 없던 것은 호스트 대면 표면 —
HIU-6 의 「명시적 해제」가 top IO 입력뿐이었다. 다섯 워드가 섰다:

| 오프셋 | 워드 | 실물 |
|---|---|---|
| `0xF80` | FAULT_STATUS (RO) | 열아홉 축 중 열일곱의 sticky 배치 + `[6]` 폴딩. `[17]` 엔트로피와 `[18]` 명령 디스크립터는 세울 원천이 미착지라 상수 0 |
| `0xF84` | FAULT_CLEAR (WO, W1C) | 각 하위 유닛의 `faultClear` 에 **논리합**으로 들어간다 — 기존 IO 해제선을 무효화하지 않는다 |
| `0xF88` | FAULT_SUMMARY (RO) | `[0]` = STATUS 논리합. 개별 노출을 대체하지 않고 덧붙인다 (§5.6 1항) |
| `0xF8C` | CAP_STATUS (RO) | 정본 축 **넷** 중 **셋**이 배선됐다 (2026-09-21 CAP_STATUS 파도, `host/CapStatusWord`) — `[0]` 재조립 슬롯 용량(sticky 는 Reassembly 안, 워드는 레벨 통과) · `[1]` step 프로그램 미상주 · `[2]` EH 사슬 용량(DecodeWalk 종결 등급을 `oValid` 로 유효 한정한 sticky — 쓰레기 헤더로 서지 않는다). `[3]` 연산 미지원은 세울 원천 자체가 0건이라 상수 0 (아래 「자리는 있고 회로는 없다」 표 · 정본 E.1.3). `[31:4]` = 0. **fault 아님** — STATUS·SUMMARY 어느 쪽에도 들지 않는다 (§1.6.2) |
| `0xF90` | CAP_CLEAR (WO, W1C) | 같은 비트 배치. 예약 구간은 정본대로 `[31:4]` (`Fault.N_CAP_BITS = 4` 에서 유도, 컴포넌트의 자기 마스크와 elaborate 시점 `require` 로 대조). 예약 위반 기입은 **한 비트도 내리지 않고** 거절 + loud (`FAULT_STATUS[6]`) — 축 넷 전부의 적법한 W1C 가 수락된다. 발화와 해제가 같은 사이클이면 발화가 이긴다 (StickyFault 규약 승계). 후-formal: `rtl/formal/sby/CapStatusWord/capword.sby` (선-formal `CapWord.tla` 가드 넷) |

`[6]`「거절된 구성 기입」이 세 원천을 접는다 — `MmioConfig.faultBadWrite` ·
top 의 `cfgSurfBadWrite` · **완료 유닛의 새 `faultBadWrite`**. 상류
관측면(`io.fault.*`)에서는 접지 않고 이 워드에서만 합류하며, 폴딩 지점을
명시하라는 §5.6 3항의 이행이다. `[16]` 링 오버플로의 해제도 이제 여기다 —
완료 유닛은 `io.faultClearOverflow` 입력으로 그 펄스를 받는다.

능력 부재 워드의 sticky `[1]`·`[2]`·`[3]` 은 `host/CapStatusWord` 가 든다
(2026-09-21 파도 — 착지 당시엔 top 이 `[1]` 하나를 직접 들었다). StepSequencer
의 `oCapAbsent` 도 DecodeWalk 의 `oCapAbsent` 도 종결 등급 1펄스/레벨이라
관측면이 놓칠 수 있는데, 정본 E.1.2 가 「능력 부재도 관측이 sticky 여야
재시도 주체가 놓치지 않는다」고 정했다. `[0]` 만 원천(Reassembly)이 자기
sticky 를 들어 워드는 레벨을 통과시키고 수락된 W1C 를 그쪽 clear 로 돌려준다
(이중 sticky 레이스 회피). fault 축 열일곱은 배치일 뿐 새 상태가 아니고,
`[17]`·`[18]` 둘은 배치도 아니다 — 세울 원천 자체가 미착지라 상수 0 이다.

### 미측정 — 단언이 없는 계약 (§6.7 원칙 5)

**E.12.1 5항 후단 — 「스테이징된 태그를 관측면에 내지 않는다」 — 좁혀졌다 (2026-09-26).**
전단은 `AbortStaging_props.sv` 의 `t_arm_src_0/1/2` 가 잰다. 후단의 *조립 국소 경로* —
`0xF40`–`0xF7C` 전 오프셋의 읽기 값(`0xF58` = `{29'd0, armed}` · `0xF50`/`0xF54` =
재조립 출력의 영확장 · 나머지 0)에 스테이징 태그가 한 비트도 실리지 않는다 — 는 이제
`rtl/formal/sby/Wt64Top/assembly.sby` 가 잰다 (`a_rd_arm` · `a_rd_acnt` · `a_rd_ainc` · `a_rd_wo`).

**남은 것 — Reassembly 경유.** 스테이징 태그는 발화와 무관하게 `reasm.io.abort.tag` 에 상시
결선되고 `0xF50`/`0xF54` 는 Reassembly 출력이다. 그 출력이 태그 값에 의존하지 않는다는
것은 `abortCount` 만 `t_ab_cnt_hold` 로 덮이고 `incomplete` 는 라벨이 없다 — 2사본 miter 후보.
한동안 이 자리에 `p_arm_width` 가 있었는데 3비트 포트에 대한 항진명제였다 (`connect \A 1'1`)
— **셀 수로는 잡히지 않는 공허의 셋째 결**이다. 조립층 태스크는 계층 모델이라 그 상수 접힘
검사가 모듈 경계를 넘지 못한다 — 그래서 그 태스크의 반증력은 머리의 역-변이 표가 든다.

**완료 구역·fault 표면의 오프셋 배타성 — 조립 절반이 섰다.** 다른 구역 접근이 완료 유닛을
스트로브하지 않는다(`a_cq_strb`) · `0xF84` 해제 라우팅(`a_fclr_b*`)은 측정. 구역 *안쪽*
배타성(정의 워드 밖 기입이 레지스터를 움직이지 않음)은 `CompletionUnit` 하네스 몫으로 남는다.

**CAP_STATUS 워드의 top 결선 셋 — 측정 (2026-09-26).** 축 `[0]` 의 `clrAcc(0)` →
`reasm.io.capAbsentClear` 합류(`a_cap0_clr`, 해제선 `io.faultClear.reasmCap` 은 자유 입력) ·
축 `[2]` set 의 `oValid` 유효 한정(`a_cap2_rise`) · 축 `[3]` 읽기 0(`a_rd_capb3`, MMIO 표면 —
미구현을 고정하는 단언이라 원천이 서면 옮긴다). 남는 것: 축 0 의 sticky 는 Reassembly 의
`t_capa_next_eq` 이고 조립은 합류만 잰다 — 두 증명의 합성은 서술이며, 해제선이 둘(CAP_CLEAR
`[0]` · IO)이라 CapWord 모델의 단일 authority 문면은 최상위에서 불성립이다
(`lint_postformal._PARTIAL` 의 CapWord 두 항목이 그 좁힘을 든다).

### 자리는 있고 회로는 없다 (§3.9 등재 대상)

새 맵이 **자리와 필드를 정했으나 이 RTL 이 소비 회로를 내지 않는** 표면이다.
자리를 정한 것과 회로를 낸 것은 다른 사실이고, 섞어 보고하지 않는다 —
미측정은 통과가 아니다 (정본 §6.7 원칙 5).

「예약」과 「미배선」은 전기적으로 같다 (쓰기 무시 · 읽기 0). **다른 것은
사실이다**: 예약은 *표에 없는* 오프셋이고, 아래는 표에 *있는데* 소비자가 없는
오프셋이다. 그 구별이 코드에 보이도록 미배선 구역도 이름 있는 상수를 갖고
(`object Wt64Top` 의 `Sq`·`Xent`·`Xctl`·`Fault`·`Ident`) 디코더가 그 구역을
**열거한다** (`selSq`·`selIdent` → `selUnwired`). `selXent`·`selXctl` 은 파도 3
(2026-09-26)이 `XlateStaging` 으로 배선해 그 열거를 떠났다 — 아래 「파도 3」 장.

| 표면 | 오프셋 | 상태 | 부재의 실체 |
|---|---|---|---|
| 명령 링 전량 | `0x380`–`0x390` | 미구현 | 명령 방향 실물 0건 — 일의 원천이 top 의 `io.instr` 외부 제시이고, 링에서 디스크립터를 꺼내는 경로가 없다 |
| 두 링의 base | `0x300`/`0x304` · `0x380`/`0x384` | 미구현 | 현행 완료 링은 *장치 상주*(내부 `Mem`)라 기저 주소를 소비하지 않는다. 완료 쪽 두 워드는 `object CompletionUnit` 의 `OFF_CQ_BASE_LO/HI` 가 이름을 들고 **어느 회로도 참조하지 않는다** — 그 사실 자체가 미배선의 뜻이다 |
| CQ_SIZE 의 *기입* 반쪽 | `0x308` | 부분 | 읽기는 실물(`log2` 재인코딩). 기입은 링이 장치 상주라 이행할 수단이 없다 — 현재 크기와 *같은* 값만 수락(무동작)이고 다른 값은 **거절 + loud** (`0xF80[6]`). 조용한 무시를 고르지 않은 이유는 호스트가 자기가 정한 크기의 링이 있다고 믿게 되기 때문이다. 링의 거처 합의(§3.10)가 서면 진짜 RW 가 될 자리 |
| 미적중 관측 3워드 + 해제 | `0xE04`–`0xE10` | 부분 | `0xE10` 해제(`[0]`, 예약 `[31:1]` 엄격)와 세 RO 워드의 쓰기 거절 + `[6]` 은 실물이다 (파도 3). 남은 것은 관측 *값* — 미적중 sticky 는 HiuPipeline 에 있으나 관측면에 나가지 않고 정지한 요청의 VPN 배선은 0건이라 세 워드의 읽기는 0 이다. 변환 항목 배열(`0xC00`–`0xDFC`)과 XLATE_FLUSH(`0xE00`) 두 행(「내부만」)은 파도 3 이 배선해 이 표에서 물러났다 |
| FAULT_STATUS `[17]` 엔트로피 | `0xF80[17]` | 미구현 | 비트 *자리*는 ABI 로 확정됐고 **세울 원천이** 없다 — 엔트로피원 유닛 자체가 재구현에 미착지다. 생성물에서 상수 0 (`faultWords_status[17] = 1'b0`). 해제 경로도 참조되지 않아 회로가 서지 않는다 |
| FAULT_STATUS `[18]` 명령 디스크립터 | `0xF80[18]` | 미구현 | E.5.4 가 만든 새 원천 (모르는 kind · 예약 비0 · 부적법한 길이). 명령 링 소비자가 미착지라 세울 주체가 없다 — `[17]` 과 같은 부류·같은 처분이며 생성물에서 상수 0 (`faultWords_status[18] = 1'b0`) |
| CAP_STATUS `[3]` 연산 미지원 | `0xF8C[3]` | 미구현 | 정본 E.1.2 가 1장 1.6.2 의 넷(EINSUM 패턴 · 순열 형태 · 브로드캐스트 · 축약)을 한 축에 접었는데 지원 여부를 판정하는 회로가 재구현에 0건이다. 워드 컴포넌트의 sticky 는 일반 계약이라 남아 있고 top 이 set 을 False 로 묶는다 — 생성물에서 `capSet_3 = 1'b0`. `[2]` 는 2026-09-21 파도가 배선해 이 표의 대상이 아니다 |
| HIU_ABI_VERSION | `0xFFC` | 미구현 | 자리는 되살렸으나 **판 번호가 §3.10 합의 대상**이다 — 틀린 값을 내는 것이 값을 안 내는 것보다 나쁘다 |

### 워드 안의 예약 비트 — 엄격 (결정 A 와 같은 형태)

새로 배선된 워드 중 예약 비트를 가진 넷에 거절 경로를 냈다. 비0 기입은
**거절 + loud sticky fault** 이며 마스크는 적재 마스크의 여집합으로 유도한다
(`MmioConfig.LNID_RSV_MASK` 선례 — 두 상수가 따로 표류할 자리를 없앤다):

| 워드 | 예약 | 마스크 |
|---|---|---|
| MASK_NONCE_PART `0xEA0` | `[31:8]` | `0xFFFFFF00` |
| MASK_REKEY `0xEBC` | `[31:8]` | `0xFFFFFF00` |
| FP_BIND `0xF04` | `[30:24]` | `0x7F000000` |
| ABORT_TAG1 `0xF44` | `[27:16]` (poison · trace · 예약 — 파도 4 D2) | `0x0FFF0000` |
| ABORT_TAG2 `0xF48` | `[31:16]` | `0xFFFF0000` |
| ABORT_FIRE `0xF4C` | `[31:1]` | `0xFFFFFFFE` |
| CQ_SIZE `0x308` | `[31:5]` | `0xFFFFFFE0` |
| IRQ_MASK `0x324` | `[31:1]` | `0xFFFFFFFE` |
| IRQ_CLEAR `0x328` | `[31:1]` | `0xFFFFFFFE` |
| FAULT_CLEAR `0xF84` | `[31:19]` | `0xFFF80000` (E.5.4 의 `[18]` 신설 반영 — `Fault.N_BITS` 에서 유도) |
| CAP_CLEAR `0xF90` | `[31:4]` | `0xFFFFFFF0` (`Fault.N_CAP_BITS = 4` 에서 유도 — 판정은 `host/CapStatusWord` 가 하고 top 은 `rsvBad` 를 `[6]` 에 합류시킨다) |

앞 넷은 `top/Wt64Top.scala` 가, IRQ_MASK 는 **정규화에서 거절로 바뀌었다** —
옛 착지는 `wdata & 1` 로 정규화해 저장했는데 정본 E.1.2 가 이 워드의
`[31:1]` 을 *엄격*으로 못박았다. CQ_SIZE·IRQ_MASK·IRQ_CLEAR 의 거절은 완료
유닛이 자기 sticky (`io.faultBadWrite`)로 들고 `0xF80[6]` 에서 합류한다.
같은 구역의 **RO 오프셋 쓰기**(CQ_TAIL · IRQ_STATUS · 엔트리 창 · 드레인
여섯 · CQ_OCC · ALLZERO)도 같은 sticky 로 거절된다 — 마스킹·step·소거 구역이
이미 하던 처분과 같은 형태이며, 완료 구역만 관대하게 두면 같은 페이지 안에서
처분이 갈린다.

거절은 하나의 새 sticky (`io.fault.cfgSurfBadWrite`, 해제 `io.faultClear.
cfgSurfBadWrite`) 로 접힌다. `MmioConfig` 의 `faultBadWrite` 와 **접지 않은**
이유는 원천 모듈이 다르기 때문이다 — 하위 유닛의 sticky 를 top 이 대신 들 수
없다. 호스트 대면 표면(`0xF80[6]` 「구성 — 거절된 구성 기입」)에서 한 비트로
합류하며, **그 표면은 둘째 파도에서 착지했다** — 폴딩은 이제 실물이다.

FP_PROG 의 용량 밖 슬롯·색인과 step 워드 예약 비트는 **StepSequencer 가 이미**
자기 계약으로 거절하고 `faultBadProg`(새 맵 `0xF80[15]`)로 크게 알린다 —
top 에서 두 번 검사하지 않는다. 검사가 두 곳에 있으면 둘이 갈리고, 그때 어느
쪽이 정본인지 답할 수 없다.

## 완료 디스크립터 · 명령 태그 사이드밴드 — 호스트 ABI 결정 4·5 (2026-08-25)

B.5 의 두 행이 **한 서명**으로 닫혔다. 태그는 명령 방향에서 호스트가 만들어
넣고 완료 방향에서 돌려받으므로, 두 표면의 직렬화가 갈리면 호스트 SDK 에 태그
코덱이 두 벌 생기고 그 드리프트가 정본 §1.4.4 「태그 조립은 한 곳에서」가 이름한
실패형의 *호스트 판*이 된다. 그래서 두 행을 따로 닫지 않았다.

### 결정 4 — 명령 제시의 태그 동반: 사이드밴드

명령 워드열과 태그가 같은 beat 에 나란히 오고 태그는 독립 valid 를 갖지 않는다
— 명령 valid 하나가 둘을 함께 유효화한다 (E.10 「도착의 원자성」의 재사용).
정본이 이미 닫은 갈래 둘이 나머지를 배제한다: §1.1 정의(태그는 명령어 인코딩의
일부가 *아니다*)가 명령 스트림 워드 갈래를, E.10 규범 1항이 채널 분리를.

**사이드밴드가 나르는 태그는 *통째*다** (E.5.4 규범 3항) — 워드 표면이 아니므로
E.5.1 세 워드 직렬화의 대상이 아니다. 명령 디스크립터는 *호스트 메모리 쪽 형태*
이고 사이드밴드는 *장치 안쪽 제시 형태*이며, 둘을 잇는 것은 「1 디스크립터 = 1 명령
+ 그 태그」다. 그래서 `Wt64Top.io.instr.tag` 는 `Types.Tag` 번들 그대로다.

> 이 파도가 한때 그 자리를 다섯 워드 포트로 바꿨다가 되돌렸다. 정본이 확정한
> 직렬화는 다섯이 아니라 셋이었고, 무엇보다 *사이드밴드는 직렬화의 대상이
> 아니었다* — 워드 표면이 아니기 때문이다. 번들 포트에는 예약 여백이 아예 없으므로
> 「검사받지 않고 통과하는 비트」(§5.7)도 생기지 않는다. 여백은 워드 표면에만 있고,
> 그 표면의 처분은 *방향*이 정한다 (E.5.1 4항).

### 결정 5 — 디스크립터 두 벌: 워드 정렬 + 선두 kind 바이트

정본 E.5.1(태그 직렬화) · E.5.2(kind) · E.5.3(완료) · E.5.4(명령)가 배치를
확정했다. **태그는 세 워드다** — 80 = 32 + 32 + 16.

| 상대 | 완료 (kind=`0x01`) | 명령 (kind=`0x02`, **UNWIRED**) |
|---|---|---|
| `+0x00` | CD_KIND `[7:0]`=`0x01` · `[31:8]` 예약 0 | SD_KIND `[7:0]`=`0x02` · `[31:8]` 예약 0 |
| `+0x04` | CD_TAG0 `[31:0]` wave | SD_TAG0 — 같음 |
| `+0x08` | CD_TAG1 `[31:16]` 스레드 · `[15:0]` LNID | SD_TAG1 — 같음 |
| `+0x0C` | CD_TAG2 `[31:16]` 예약 · `[15:8]` 정밀도 · `[7:0]` 차원 | SD_TAG2 — 같음 |
| `+0x10` | CD_BASE `[7:0]` 결속 LBID | SD_BODY_LO 본문 주소 `[31:0]` |
| `+0x14` | CD_TOTAL `[31:0]` 조각 총개수 (그릇) | SD_BODY_HI 본문 주소 `[63:32]` |
| `+0x18` | CD_RSV0 = 0 | SD_LEN `[15:0]` 본문 워드 수 |
| `+0x1C` | CD_RSV1 = 0 | SD_RSV = 0 |

단일 출처는 `host/CompletionUnit.scala` 의 `object HostDesc` 하나이고, 태그 세
워드가 두 방향에서 같은 상대 오프셋 `+0x04`~`+0x0F` 에 선다는 것은 주석이 아니라
그 객체의 `require` 다 — 방향 고유 워드가 *전부 태그 구간 뒤*에 있다는 것이 그
성립 조건이고 그것을 elaborate 시점에 강제한다.

태그가 kind 바로 뒤인 이유는 그것이 두 방향이 *공유하는 유일한 블록*이기 때문이다.
뒤에 두면 명령 쪽 본문 참조가 넓어질 때 태그가 밀리고 그 순간 「같은 상대 오프셋」이
깨진다. CD_TOTAL 이 워드 하나를 전량 쓰는 것도 같은 원리의 다른 축이다 — E.10 4항이
총개수 폭을 정하지 않았으므로 *폭이 확정된 것(LBID)을 먼저 앉히고 미확정을 뒤로 민다*.

명령 본문이 참조인 이유는 산술(416b = 52 B > 32 B)만이 아니다. §1.3 은 그 상한을
「형상 파라미터이지 ISA 상수가 아니다」라고 적으므로, 본문을 품는 디스크립터는 폭이
형상의 함수가 된다 — 디스크립터는 드라이버 구조체이고, E.1.2 해설이 「바이너리도
드라이버 구조체도 형상에 닿지 않는다」고 적은 둘 중 하나가 닿게 된다.

**kind 는 되돌림의 수단이다** — 배치 개정이 새 kind 값의 *단조 추가*가 되고 옛
호스트는 모르는 kind 를 *건너뛴다*(head 한 칸 전진). 건너뛰기가 가능한 것은 32 B
고정 폭 때문이며 — 가변 길이였다면 모르는 항목의 길이를 몰라 링이 그 자리에서
영구히 멈춘다 — **고정 폭이 되돌림의 전제다**. 두 방향이 *한 값 공간을 나눠 쓰므로*
잘못된 링에 놓인 디스크립터가 탐지 가능하다. `0x00` 은 부적법이다 — 0 으로 남은
링 칸이 적법한 디스크립터로 읽히지 않게 한다.

E.5.4 가 fault 축을 하나 신설했다: **FAULT_STATUS `[18]` 명령 디스크립터
malformation** (모르는 kind · 예약 비0 · 부적법한 길이). 명령 링 소비자가 미착지라
세울 원천이 없어 상수 0 이며, `[17]` 엔트로피와 같은 부류다. `N_BITS` 를 19 로
올렸고 FAULT_CLEAR 예약이 `[31:19]` 로 따라 움직였다 — 그 마스크가 `N_BITS` 에서
유도되므로 실제로 고친 자리는 상수 하나였다.

**여백 정책 — 돌려주는 쪽으로 확정**: 장치가 매 항목 32 B *전량*을 기입하고
(예약은 0), 호스트는 예약을 무시한다. §5.7 함정이 요구한 「어느 쪽인지 함께
적기」의 이행이며, §5.7 의 malformation 정책(받아들이는 쪽)을 여기로 옮기지
않는다. 전량 기입이 *의무*인 이유는 잔류다: 32 B 칸에 12 B 만 갱신하면 그 칸의
이전 항목 태그가 남고 호스트가 그것을 새 완료로 읽는다 (§3.6.3 해설이 flush 에
대해 경계한 것과 같은 형태). 구현에서 그 의무는 **색인 0..7 위의 전사 함수**로
이행된다 (`HostDesc.completion`) — 미정의 워드가 존재할 수 없으므로 전량 기입이
검사가 아니라 구조다.

### 80b 팩킹 순서는 *미확정*으로 남는다 — 그리고 그것이 요점이다

`Common.scala` 의 태그 주석이 「비트 오프셋은 어셈블러 관측으로 확정할 것」이라
적고 그 관측을 기다리고 있었다. **그 관측원은 원리적으로 비어 있다** — §1.1 이
태그를 인코딩 밖에 두었으므로 어셈블러는 태그를 방출하지 않는다. 즉 확정의
조건은 관측이 아니라 *결정*이며, 주석을 그렇게 정정했다.

그 사이 잠정 배치(`asBits` 가 함축하는 순서)가 생성된 SV 한 줄로 굳고 있었다.
부록 B 해설의 「조용히 메운 공백은 메워지지 않은 것보다 위험하다」와 같은
형태이고, 여기서는 모델이 아니라 생성물이 메웠다. 워드 정렬 직렬화는 그 공백을
*동결하지 않고* 두 표면을 닫는 방법이다 — 필드당 한 워드라 80b 여백이 크지만,
그 여백이 사는 값이 「정본이 정한 적 없는 값을 호스트 파서의 계약으로 굳히지
않는 것」이다. 조립·분해는 `Types.Tag.toWords`/`fromWords` 단 한 곳.

### 태그 워드 코덱이 세 표면을 함께 움직인다

E.5.1 은 이 배치를 「새로 만든 것이 아니다」라고 적는다 — E.1.2 「재조립 문맥 소거」의
`0xF40`~`0xF48` 세 워드가 이미 같은 배치였고, E.5.1 이 그것을 세 표면(완료 디스크립터 ·
명령 디스크립터 · 소거 스테이징)의 *공통* 직렬화로 올렸다. 그래서 이 파도는 소거
스테이징도 `Types.Tag.fromWords` 로 돌렸다 — 앞판은 그 자리에서 필드를 손으로
쪼개고 있었고, 공통 직렬화가 선 뒤로 그것은 저장소 안에 코덱을 두 벌 두는 형태다
(§1.4.4 가 이름한 드리프트 실패형의 축소판).

스테이징은 *정의 비트만* 든다. TAG2 예약 `[31:16]` 은 엄격 거절이라 비0 이면 기입
자체가 서지 않으므로 저장할 값이 없고, 그럼에도 저장하면 §5.7 해설의 「무시되는 비트가
*어딘가에 저장되거나* 반향되면」의 그 저장이 이 레지스터가 된다. 발화 시점에는 같은
함수(`reservedNonZero`)로 한 번 더 본다 — 「검사가 두 곳」이 아니라 *정의가 한 곳이고
걸린 자리가 둘*이라 갈릴 수 있는 형태가 아니다.

`A_TAG2_RSV` 마스크도 이제 코덱 상수에서 유도한다 (`Types.Tag.TAG2_RSV_LO`) — 같은
값을 두 곳에 적으면 그 순간부터 어느 쪽이 정본인지 답할 수 없다.

### 후-formal — 이 축의 첫 태스크 (0건이었다)

완료 디스크립터·명령 링에는 후-formal 태스크가 **0건**이었다. 배치를 바꾸면서
재는 것을 만들지 않으면 바뀐 것이 무엇을 보증하는지 아무도 모르는 상태가 그대로
이어진다. `rtl/formal/sby/CompletionUnit/descriptor.sby` 가 그 첫 태스크다
(`VERIFIES` 앵커 5 — 모델 가드가 없는 모듈이라 `PROVES` 가 아니다,
OperandDecode 선례).

머리 속성은 **「링 칸 전량 기입 · 잔류 부재 · 워드 배치」가 한 등식**이라는 것이다
— 되읽은 여덟 워드가 전부 *이번* push 의 입력 필드로 독립 재구성한 값과 같다.
정본 함정이 이름한 위험이 정확히 이것이다: 링 칸에는 변환 저장의 유효 비트 같은
방벽이 없어 — head·tail 은 「이 칸이 유효한가」만 말하고 「어느 바이트가 이번
것인가」는 말하지 않는다 — *잔류가 곧 오독*이고 전량 기입이 방벽을 대신한다.
잔류의 일반형은 「그 칸에 원래 있던 임의의 내용」이고 링 저장소에 reset 이 없으므로
**형식 검사의 초기 상태가 바로 그 임의 잔류다** — 한 번의 push 로 잔류 검사가
성립하는 이유가 이것이다. 부분 기입은 초기 내용의 모델링 방식과 무관하게 잡힌다:
미기입 워드는 초기 내용을 내는데 기대값은 자유 입력의 함수이므로 반례가 존재한다.

재지 않는 것도 태스크 머리에 적었다 — 명령 방향(회로 없음, elaborate require 가
든다) · k-귀납(링 저장소가 포트로 노출되지 않아 불변을 적을 수 없다; BMC 는 덮인
깊이 안에서 전수다) · 드레인 집계/IRQ/거절 축(후속 파도).

### ⚠ 함정 실측 — 하네스가 참조하는 이름이 *소스 줄 번호*에 매여 있다

SpinalHDL 은 익명 `when` 조건 신호를 **소스 줄 번호**로 이름 짓는다
(`when_<파일>_l<줄>`). `Reassembly_props.sv` 가 `when_Common_l141` 을 그 이름으로
참조하고 있었는데, 이 파도가 `Common.scala` 를 늘리자 그 이름이 `when_Common_l259`
가 됐다. Reassembly 하네스는 bind 문을 대상 모듈 본문으로 *텍스트 전개*하는 방식
이라 없는 이름이 **암묵 wire** 로 살아나 자유 신호가 됐고, 그 위에 선
`p_ab_not_fault_src` 가 FAIL 했다.

**크게 실패한 것은 다행이다** — 공허 PASS 였다면 이 파도가 그것을 통과시켰다.
그리고 그 태스크를 돌리게 한 것은 사람의 기억이 아니라 `scripts/sby_impact.py`
역색인이다. 그 도구가 존재하는 이유가 정확히 이 부류이고, 이번에 값을 했다.

당장의 수리는 이름을 매크로 한 줄(`WT_STICKY_SET_FAULT`)로 모은 것이다 — 다음에
밀릴 때 고칠 자리가 하나다. **근본 수리는 별 파도다**: `StickyFault` 의 set 조건에
안정된 이름을 주면 이 부류가 사라지지만, 그 개명이 StickyFault 를 쓰는 *전 모듈*의
생성물 이름을 움직이므로 하네스 전수를 함께 흔든다. 같은 형태의 참조가
`ResultBank_props.sv`(`when_ResultBank_l163/l181`) · `SharedUnit_props.sv`
(`when_SharedUnit_l192`) · `XlateStore_props.sv`(`when_XlateStore_l200`) 에도 있고,
그쪽은 각 모듈 자기 파일의 줄 번호라 이번에 흔들리지 않았다.

**SharedUnit**

- 추월 금지(FIFO 보존)를 구현이 새로 결정했다: 모델 Arrive 의 직행 분기는 serving = {} 만 요구해 보류 열이 비어 있지 않아도 새 도착이 대기자를 추월해 즉시 점유할 수 있다. RTL 은 acceptDirect 에 queueEmpty 를 추가로 걸어 추월을 금지했다 (FAB-6 도착 순서 공정성의 이 지점 형태). 모델에 no_overtake 가드로 돌려보내 검증할 것을 제안
- 배압 무시 → loud fault 경로가 모델에 동작으로 없다: 모델은 backpressure 가드 삭제 실험(조용한 소실)으로만 그 자리를 덮는다. RTL 은 §2.2/§2.6 대로 위반을 sticky fault 로 구현했고, 위반 갈래가 어떤 상태(슬롯·본체·카운터)에도 쓰지 않음(FAB-10 소비자 무결성)도 함께 구현했다 — 모델에 violating-push 동작 + fault_raised/fault_sticky/bp_…
- 동시성 결정: 모델은 Arrive/Dequeue/Complete 가 원자적 인터리빙이라 같은 순간의 도착+dequeue 가 없지만, RTL 은 한 사이클에 둘이 겹친다. 가득 찬 열에서 pop 하는 사이클의 도착은 보수적으로 배압 처리했다 (room 판정은 현재 cnt 기준, pop 이 비운 자리는 다음 사이클부터 보인다) — 배압은 오류가 아니므로 적법하나 모델이 모르는 결정
- 본체 인터페이스 계약을 구현이 정의했다: start 는 busy 낮은 사이클에만 서고(처분 구조가 보장), busy 는 start 다음 사이클부터, done 은 완료 사이클 1사이클 + rsp 동시 유효. 모델의 Complete 에 대응하는 RTL 문면이며 본체 교체(자리 표시자 → 실제 나눗셈·행렬 유닛)의 고정 경계

**ResultBank**

- 나이 카운터는 0..L 만 표현한다 (모델은 0..L+1). 근거: 해제가 age === L 판정과 같은 블록에 융합돼 있어 age > L 이 구조적으로 생성 불가능 — 위반 상태를 저장할 별도 검사기가 감시할 전이가 없다. 이 융합을 깨는 개정은 L+1 표현과 검사기를 함께 들여와야 한다고 파일 머리에 못박았다 (모델 해설의 「판단하라」 지점에 대한 답).
- 획득 거절의 관측 형태: 모델은 acquire_free 가드가 동작 자체를 막지만, RTL 의 요청은 배선으로 도착하므로 「막힘」을 granted === False 의 명시적 같은-사이클 응답으로 만들었다 — FAB-2 의 「무처분 없음」 어휘를 획득 경로에 적용한 결정. 모델에 거절 관측 변수는 없다.
- 소유는 허가 다음 사이클부터 관측된다 (레지스터 갱신) — 구간 시작 t 는 허가+1 사이클이고, 허가와 같은 사이클의 기입은 자격 없음으로 fault 다. 모델에선 Acquire 와 Write 가 별개 원자 단계라는 사실의 RTL 시간축 해석이며, 모델이 명시하지 않은 결정이다.
- 범위 밖 물리 슬롯 색인 (slotCap 이 2^k 가 아닐 때 존재): 기입은 자격 없음으로 접어 같은 sticky fault, 획득은 거절, 읽기는 owned=False. 모델의 Slots 는 불투명 토큰이라 색인 공간이 없다 — 이 처분은 전부 RTL 의 신규 결정이다.
- 소유 해제는 store 를 지우지 않는다 — 값은 구간 종료 후에도 남아 후속 참조(§2.4 정의)에 쓰인다. 모델의 Tick 이 val 을 UNCHANGED 로 두는 것과 정합하지만, 읽기 포트 의미론 자체가 모델 밖이다.
- lastWriter 상태를 RTL 에 두지 않았다 — FAB-4 아래 구간당 기입자 최대 1 (정본 해설: 3항은 공허) 이라 모델의 lastWriter 는 관측 변수로 판단. 기입자 기록을 들여오는 개정은 모델 Acquire 의 lastWriter 초기화(구간 시작 시 기록 재시작)를 함께 들여와야 한다고 주석에 남겼다.

**FabricMerge**

- 선택 기전을 확정했다 — 모델은 선택 기전을 짓지 않고 공정성만 SF 가정으로 걸었는데(Fabric.tla 「공정성」절), RTL 은 one-hot 포인터 라운드로빈(fire 마다 ptrOh := selOh.rotateLeft(1))으로 기전을 세웠다. 모델 자신이 적었듯 「어떤 RTL 이 그 공정성을 갖는지는 후-formal 의 몫」 — 이 라운드로빈이 SF_vars(Grant(p)) 를 실현하는지가 후-formal 검사 대…
- 제공 잠금(lock)을 추가했다 — valid && !ready 동안 selOh 를 lockedOh 로 동결한다. 모델에는 없는 결정이다(모델은 시도 사이에 선택이 바뀌어도 된다). Stream 페이로드 안정성(소비자 관측 안정)을 위해 필요했고, single_producer 를 강화할 뿐 진행성은 해치지 않는다(포인터는 fire 에만 돈다). 모델에 반영하려면 「잠금 중 선택 불변」을 선택 규칙의 속성으로 되돌려 보낼 수 있…
- 배압 위반 표면을 옮겨 읽었다 — 모델의 Shove(~ready 에서 병합 지점 구동)는 이 RTL 에서 구조적으로 불가능하다(pop 이 fire 연언). 물리적으로 남는 위반 표면은 생산 경계(가득 찬 출력 자원에 strb)이고, sticky fault 계기는 거기 있다. §2.6 진행 전파 규범이 「기계 안의 각 소비자」에 배압 규약을 지우므로 이 경계도 §2.6 4항의 적용 지점이라고 읽었다 — 이 독법이 맞는지 모델/정…
- 위반 데이터의 처분을 「소거 + loud fault」로 확정했다 — 모델의 Shove 는 규약 위반 pop(값이 넘어간다)인데, RTL 의 shove 는 값이 자원에도 소비자에도 닿지 않고 버려지며 sticky fault 만 남는다. FAB-5 의 「재시도되거나 fault 를 낸다」 중 fault 갈래의 실현이다.
- 출력 자원을 시프트 큐로 구현 — pop 시 내용을 지우지 않아 마지막 항목을 넘긴 face 에 낡은 값이 남는다(모델의 dat 잔존과 동형). 그 값의 격리는 자원이 아니라 병합 게이팅이 맡는다 — 두 축의 분리를 그대로 유지.
- D 의 값은 여전히 미확정 — Wt64Config.outDepth(기본 1) 파라미터로 유지했고 N=3·D=2 형상 elaborate + lint 로 파라미터화만 검증했다. 값 확정은 정본 §2.6 대로 측정과 함께.

**XlateStore**

- VA/PA 전체 폭을 VA_W = PA_W = 44 로 확정했다 — 정본은 E.2 에서 항목 8 B·페이지 4 KiB·필드 목록만 주고 주소 폭을 주지 않는다. 44/44 는 기본 형상(파티션 4 × 색인 16)에서 항목이 정확히 8 B 를 채우는 값이다 (유효 1 + 권한 3 + 태그 28 + 프레임 32 = 64b, 예약 비트 없음). 정본 E.2 에 폭 확정이 필요하다.
- 항목 본체의 비트 배치(하위부터 tag → frame → perm r/w/x, 유효 비트는 Mem 밖 레지스터)를 구현이 정했다 — E.2 는 필드 목록만 준다. **닫힘 (파도 3):** 호스트 쪽 문은 8 B 를 직접 기입하는 창이 아니라 두 워드(E.1.2 XLATE_ENTRY_LO/HI)이고 ABI 는 그 워드 배치다. 내부 본체 배치는 ABI 에 닿지 않는다 — 단 HI `[30:28]` 의 R·W·X 비트별 배정은 정본이 나열 순서로만 주어 §3.10 입력으로 올렸다 (아래 「파도 3」 장).
- flush(p) 가 파티션 p 의 진행 중 채움 버퍼 줄도 함께 취한다 — XlateStore.tla 에는 채움이, Isolation.tla 에는 flush 가 없어 flush × 채움 상호작용이 어느 모델에도 없다. 이 결정이 없으면 flush 뒤 이전 컨텍스트의 줄이 커밋돼 HIU-2 가 창 하나만큼 깨진다. 모델에 Flush 가 fill 버퍼를 소거하는 동작으로 추가돼야 한다.
- 채움 커밋 직렬화: Mem 쓰기 포트가 하나라 점유 슬롯 중 고정 우선순위(낮은 파티션 번호 우선)로 사이클당 하나씩 커밋한다. Isolation.tla 의 SubjectFillCommit 은 단일 주체라 중재가 없다 — 다중 파티션 동시 점유 시의 커밋 순서는 모델에 없는 결정이다 (기입 원천이 호스트 구성 표면 하나라 유입도 사이클당 1이라 밀림은 유한).
- install.ready 는 자기 슬롯 점유 외에 같은 파티션 flush 와의 같은 사이클 충돌도 거부한다 (기입 유실 대신 배압) — 모델에 없는 결정. (파도 3 이후 조립에서는 그 충돌이 구조적으로 불도달이다 — 설치와 flush 의 원천이 MMIO 문 하나라 한 사이클에 한 워드뿐이고, 조립 하네스가 `a_xonehot` 로 떠맡는다. 유닛 방어는 유닛 하네스 몫으로 남긴다.)
- 조회 입력을 VA 가 아니라 VPN(32b) 으로 받는다 — 페이지 오프셋은 변환에 관여하지 않으므로 받지 않는 인터페이스 선택.
- flush 효과는 다음 사이클부터 관측된다 (레지스터 경계 1개) — §3.6.3 검증 시퀀스(flush 후 조회)에는 영향 없음.

## 페이지 소유권 전이 인코딩 — 명령을 오프셋으로 (2026-08-25)

정본 개정과 같은 파도에서 착지했다. E.7 전이가 `0x204` OWN_DATA 의 `[31]` 에
방향 비트를 싣고 `[30:0]` 에 프레임을 싣던 것을, **이양용·회수용 오프셋을
따로 두는** 형태로 바꿨다 — `0x200` OWN_IDX (RW) · `0x204` OWN_STATUS (RO) ·
`0x208` OWN_SET (WO) · `0x20C` OWN_CLR (WO). 워드 선택은 `addr[3:2]` 전수
디코드다 (E.1.2: `addr[3]` = 조회 쌍/전이 쌍 · `addr[2]` = 쌍 안의 방향).

전이는 여전히 **한 워드 쓰기 한 번**이라 E.7 원자성 논증은 한 글자도 바뀌지
않는다. 얻은 것은 기계 안의 주소 용량이 *하나*가 된 것이다 — 앞판은 소유권
31b · 변환 32b 였고, 그 어긋남이 「유효하게 사상되지만 결코 장치 소유가 될 수
없는 페이지」라는 §3.4.1 밖의 *제3 상태*를 만들었다. 더 나쁜 쪽은 기입 시점
별칭이었다: 드라이버가 `(1<<31)|F` 를 조립하면 F 의 최상위 비트가 방향 비트와
겹쳐 *다른 페이지가 조용히 장치 소유로 넘어갔다.*

제거된 좁힘 배선: `MMIO_FRAME_W(=31)` · `DIR_BIT(=31)` · 조회의 `qHighZero` ·
상태 읽기의 `idxHigh0` · `require(frameW >= MMIO_FRAME_W)`. 태그 폭이 25→26b
가 됐다 (색인 6 + 태그 26 = 프레임 32 전폭).

## 재조립 문맥 소거 — 호스트 ABI 결정 A·B·C (2026-08-25)

B.5 「E.12 의 32b 버스 실물」이 물어본 것 중 자리와 배치는 앞선 결정들이 이미
답했고, 남아 있던 것은 *의미론* — 「세 워드의 기입이 무엇을 성립시키는가」 —
하나였다. 이 파도가 그것을 닫는다. 정본은 E.12.1 (무장 규율) · E.12 1항 개정
(구간 데이터) · §4.3 「소거 후 재사용」 이고, 아래는 그 RTL 대응이다.

### 결정 A — 무장 규율 (`wt64.top.AbortStaging`)

태그 80b 는 32b 워드에 들어가지 않으므로 E.7 의 「전이는 한 번의 쓰기로
완결된다」를 이 표면에 옮겨 적는 것이 *불가능*하다. 앞판은 스테이징+발화로
대신하면서 「발화 전 부분 기입 무효과」를 계약이 아니라 관행으로 두었다.
이제 넷이 기계 강제다:

| 항 | 실물 |
|---|---|
| 워드별 무장 | 태그 세 워드의 *수락된* 기입이 각각 자기 무장 비트를 세운다 (거절은 세우지 않는다) |
| 발화 조건 | 무장 셋 완비에서만 발화. 미완 발화는 **무시** — fault 도 소거 카운트도 아니다 (E.12 3항과 같은 처분) |
| 잔류 소진 | 수락된 발화 워드 기입은 소거의 성립 여부와 무관하게 무장을 전부 내린다 → stale staging 구조적 부재 |
| 관측 | `0xF58` ABORT_ARM `[2:0]` RO (§5.8 상태 표면 부류 · 드레인 정의역 아님) |

**별 Component 로 세운 이유는 측정이다.** 결정의 요점이 「관행에서 기계 강제
속성으로」인데 잴 수 없으면 절반만 이행이다. 조립(9,500줄) 전체를 k-귀납에
올리는 것은 이 속성을 재는 값에 비해 터무니없는 비용이고, 경계에 이름을
주면 하네스가 스무 줄이다 — 새 후-formal 태스크 `AbortStaging/props`.

*경계 하나는 정본이 문면으로 답하지 않았다*: 「성립·불성립 무관」의 「불성립」이
소거의 불성립인가 기입의 거절까지인가. 후자로 읽으면 E.12.1 1항(거절은 무장을
세우지 않는다)과 3항이 서로를 부정하므로 전자로 읽었다 — 예약 비0 인 발화
기입은 *거절된 구성 기입*이라 무장을 건드리지 않는다 (TAG2 스테이징·
FAULT_CLEAR 와 같은 처분). 다른 독법이 정본이 되면 `AbortStaging.okFire` 한
줄이 따라간다.

### 결정 B — 소거는 구간 데이터까지 비운다

정본이 침묵한 자리에서 모델과 RTL 이 갈려 있었다 — `Payload.tla` 의
`ContextAbort` 는 `slots` 를 비우고, `Reassembly.scala` 는 「소유하지 않으니
상류 몫」이라 적은 채 회계까지만 비웠다. 정본이 비우는 쪽으로 정했고 RTL 이
따라간다.

**비용과 새 계약**: 전 슬롯 순회는 하지 않는다. 소거 발화와 *같은 사이클·같은
게이트*로 구간 무효화 **명령** 한 beat 를 별 면(`io.clr` → `io.reasmClr`)으로
낸다 — **1사이클 · 정지 0 · 배압 0 · 새 fault 축 0**. 순회를 고르지 않은 근거 셋:

1. *원자성* — 모델의 소거는 한 스텝이다. 순회로 펴면 「회계는 비었는데 구간은
   반쯤 낡은」 중간 상태가 slotCap 사이클 동안 관측 가능해지고, 그 상태의
   지위를 정본이 정한 적이 없다.
2. *기입 면 무간섭* — `io.wr` 은 조각 수락과 원자다 (write_atomic). 순회를 그
   면에 실으면 소거 중 도착한 조각이 기입을 잃는데, 조각 면은 스트로브라
   되미룰 수단이 없다. 별 면이면 충돌 자체가 없다.
3. *이행의 자연형* — 구간 무효화의 자연스러운 실물은 데이터 zeroing 이 아니라
   칸 유효 비트의 일괄 하강이고, 그쪽에서도 한 사이클이다.

E.12 1항 해설이 「요구를 거는 형태(스트로브·핸드셰이크)는 이 문서가 정하지
않는다」로 형태를 위임했으므로 이 스트로브는 위임 안에 있다.

⚠ **정본 환류 필요 — 무효화 이행의 완결 시점.** 「소거 후 같은 LBID 를
언제부터 재개방해도 안전한가」에 정본이 답하지 않는다. `ABORT_COUNT` 는
*명령*의 회계이지 이행의 완결이 아니다. 슬롯 소유자가 무효화를 직렬로
이행하면 그 꼬리가 새 조각열의 기입과 겹칠 수 있고, 그 경합의 처분이 없다.
(유효 비트 일괄 하강 구현에서는 창이 0 이라 문제가 없다 — 즉 이 미결은
*이행 형태에 의존하는 미결*이고, 그것이 정본에 적혀야 한다.)

*인도 경로는 대응이 없고 그것이 옳다.* 모델의 `Consume` 도 slots 를 비우지만,
모델의 `Deliver` 는 slots 를 `out` 으로 복사한 뒤 `Consume` 이 비운다. RTL 의
`io.deliver` 는 {태그·결속·총개수}만 넘기고 데이터는 구간에 남아 소비자가
읽는다 — 인도 시점에 비우면 읽기 전에 지우는 것이다. 「소비 완료」에 해당하는
사건이 이 모듈에 도착하지 않는다 (정본에 그 통지가 없다). 소거 경로에는 읽을
소비자가 아예 없다는 것이 그 비대칭의 근거다.

### 결정 C — 미완 관측은 수로 충분 (RTL 변경 없음)

`REASM_INCOMPLETE` 하나가 이행이고 신원 표면은 신설하지 않는다. 근거가
§2.3(발화의 유일한 원천은 호스트 투입)에 걸린 *조건부 결정*이라는 사실이
정본에 등재됐다 (B.5 의 새 부류). RTL 은 이미 그 형태다.

### 선-formal — 가드를 하나 쪼갰다 (배터리 재실행함)

`abort_erases` 는 회계 소거와 구간 소거를 *함께* 쥐고 있었다. 실측: 그 삭제
실험의 반례는 **전부 구간 축**이 만들고 있었고 — 회계 축만 지운 기계는
`Prop_NoSilentOverwrite` 를 통과한다 — 회계 축은 한 번도 독립으로 재어진 적이
없었다. 그 사이 RTL 은 정확히 그 「한쪽만 깨진 구현」(회계는 비우고 구간은 안
비움)이었고 배터리는 그것을 볼 수 없었다.

모델 머리가 `Consume`/`ContextAbort` 를 가른 근거 — 「한 가드로 묶으면 삭제
실험이 두 경로를 동시에 지워, 한쪽 경로만 깨진 구현이 구별 불가가 된다」 —
가 *같은 액션 안의 두 축*에도 그대로 걸린다는 것이 실측됐다. ⇒ 가드 분리의
기준은 *전이가 다른가*가 아니라 **write-enable 이 다른가**다.

| 가드 | 지우면 | 반증 속성 |
|---|---|---|
| `abort_erases` | 태그·구간은 비고 *회계*가 남는다 | `Inv_ReassemblyExclusive` |
| `abort_clears_window` (신설) | 태그·회계는 비고 *구간*이 남는다 | `Prop_NoSilentOverwrite` |

### 후-formal — 신설 속성

`Reassembly/props` (PROVES `Payload.abort_clears_window`):
`p_abort_clears_slots`(무효화 명령 == 소거 발화, 같은 게이트 — 「회계는 비웠는데
구간은 안 비웠다」 표현 불가) · `p_clr_base_*`(좌표 = 소거 대상의 결속, 결속
폐기 *전* — §4.3 「소거 후 재사용」 3항) · `p_clr_needs_hit`. 증인 다섯을 함께
신설했다 (소거 발화 · 무효화 명령 · *미완* 문맥 소거 · *회계가 실린* 문맥 소거 ·
없는 태그 무시) — 앞의 단언이 전부 등식/함의라 소거 없는 세계에서 공허하다.

`AbortStaging/props` (신설 태스크, `VERIFIES: E.12.1 …`): 무장 규율 전 항. (⚠ 파도 4 가 그 1단 결손을
`AbortSurface.tla` 로 닫고 이 태스크를 PROVES 열둘로 승격했다 — 아래 「재조립 문맥 소거의 문」 절.)
`# PROVES:` 가 아닌 이유는 앵커 규율이다 — 선-formal 모델에 대응 가드가 없다.
`Payload.tla` 는 소거를 「태그 하나를 지정한 소거 기입」이라는 의미론으로
추상하고 MMIO 워드 표면은 그 모델의 상태가 아니다. 모델에 워드 층을 들이는
것은 별 결정이며, 들이지 않는 것이 지금의 판단이다 (무장 규율은 한 모듈 안의
조합·1스텝 계약이라 k-귀납이 전수로 닫는다).

이 태스크만 `bind` 를 쓰지 않고 하네스가 대상을 **직접 인스턴스**한다.
`Wt64Top.sv` 는 모듈 스물을 담은 파일이라 「첫 `endmodule` 앞에 주입」
관용구가 *어느* 모듈에 주입될지를 생성기의 파일 순서에 맡기게 되는데, 그
순서는 계약이 아니다. 단언이 보는 것이 전부 포트라서 가능한 형태이고, 그것은
제약이 아니라 이 계약의 성질이다 — E.12.1 은 호스트 대면 계약이므로 하네스도
*호스트가 볼 수 있는 것만* 본다.

## 런타임 하네스 착지 — `rtl/sim/` (2026-08-28)

`make rtl-sim` 이 실제로 돈다. 상세는 **`rtl/sim/README.md`** — 여기에는
이 층의 규약과, 다른 층과 헷갈리면 안 되는 것만 적는다.

### 이 층이 후-formal 과 다른 것

후-formal(`rtl/formal/sby/`)은 **모듈 하나의 전 상태**를 본다. 이 층은
**생성물 한 편을 통째로 돌려 golden 실측값과 맞대조**한다. 서로 대체재가
아니다 — sby 는 「어떤 상태에서도 X」를 말하고, 하네스는 「이 80개 입력에서
값이 정확히 이것」을 말한다. `MaskUnit` 의 확산은 후자로만 확인되고
(정본 §5.2.4 — 「확산은 세어서 확인할 수 없다」), `Wt64Top.sv` 는 **어느 sby
태스크도 읽지 않으므로** 이 층이 오기 전까지 0건 측정이었다.

### 규약 넷

1. **판정은 언제나 golden 과의 정확 비교다.** `!=`·popcount·통계형 확산
   검사는 하네스에 한 곳도 두지 않는다 — 「틀린 값도 다르다」. ISA-2 순열도
   같다: `F(σ(S)) == predict(σ(S))` 가 판정이고 `F(σ(S)) != F(S)` 는
   판정이 아니다.
2. **fault 는 `io_fault*` 실포트로만 관측한다.** 시뮬 전용 단언으로 fault 를
   구현하면 합성 결과물에 그 검사가 없다. 이것은 `bind` 금지(위 혼재 경계
   표)와 같은 부류의 규율이다 — 검증 장치가 납품물에 없으면 그 검증은
   납품물에 대한 것이 아니다.
3. **skip 은 실패다.** 러너가 결과 XML 을 직접 세고 `<skipped>` 를 실패로
   집계한다. 조건이 안 맞으면 스스로 건너뛰고 통과로 보고하는 검사는
   `scripts/lint_frag_slots_dual_run.py` 가 존재하게 만든 그 사고다.
   스위트마다 테스트 건수 **하한**이 표에 있어 「0건 통과」도 성립하지 않는다.
4. **미측정 축은 이름으로 열거해 통과 계수와 같은 자리에 인쇄한다.**
   `make rtl-sim` 이 매 실행 9축 원장을 찍는다. 열거하지 않으면 다음 사람이
   「하네스가 있다」를 「그 축을 잰다」로 읽는다.

### 이 층이 재지 **못하는** 것 중 이 문서가 반드시 이고 갈 셋

- **투입 방향은 여전히 미측정이다.** 명령 링(E.5)은 회로 0건이고
  `io_instr_ready` 자체가 없다. 하네스는 설계 내부 포트 `io.instr` 를 직접
  때리므로, 확인된 ISA-1/ISA-2 는 **호스트 ABI 층위가 아니라 디코드 진입
  층위의 등가**다.
- **ISA-1 의 형상 축은 미측정이다.** `Wt64Config(nPoints=2)` 로 둘째 SV 를
  내는 `gen/GenWt64TopShape.scala` 가 없다 (선례는 `GenSharedUnit.scala:23-26`
  — 같은 패턴 20줄). 하네스는 궤적 비교기를 세우고 그것이 살아 있음을 매 실행
  양·음성 대조로 증명하되 형상 축을 잰 척하지 않는다. 그 20줄이 이 축을
  여는 유일한 잔여물이다.
- **부록 D 에 ISA-1·ISA-2 를 「증명됨」으로 올리면 안 된다.** ISA-2 는
  존재 축만 닫혔고 자리 축(소유 지점·슬롯 구간 순열)은 관측면 자체가 없다.
  ISA-1 은 자리 무관성만 닫혔다. 정직한 지위는 둘 다 **「부분」**이다.

### 결정 대기 하나 — 하네스가 조용히 굳히지 않은 것

**ISA-1 의 「관측 가능한 결과」의 외연이 정본에 없다** (§1.8 문면이
ⓐ결과값만 / ⓑ출력 전부 / ⓒⓑ+타이밍 셋 다와 양립한다). 하네스는 ⓒ로 재고
