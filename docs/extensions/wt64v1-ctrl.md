# WT64v1 확장 명세 — `Ctrl-min` (값-평면 비교) · 초안 v0.1

> ### 지위 — 확장 명세 초안 v0.1
>
> 이 문서는 base 정본(`docs/wt64v1-architecture-guide/`)에 **종속**하며 충돌
> 시 base 가 이긴다. 이 문서는 **`Ctrl-min` 확장의 계약 원천**이다 —
> `.claude-memos/ctrl_proposal.md`(제안 메모)의 authority 는 이 문서로
> 이전됐다. 그 메모의 §10 사용자 확정 다섯이 이 문서의 입력이고, 그 메모의
> 어떤 문장도 이 문서를 넘어서지 않는다.
>
> 계보: #24 파이프라인(제안 → 적대 검토 → 수정 반영본,
> `.claude-memos/ctrl_proposal.md`) → 사용자 전수 확정(2026-08-28) → #25
> 인코딩 개정 파도 착지 → 이 문서(#28). 검토가 정정한 것은 전부 반영했고,
> 검토가 반증한 문장은 싣지 않았다.
>
> **완성과 지위 판정은 별개 축이다** — `C` 명세 배너와 같다. 이 문서의 완성이
> 동결 시점을 정하지 않는다: 동결은 `T_stable` 몫이고, pre-stable 에서
> 재배정·recapture 는 정규 이벤트다 (`prestable_compat_policy`).
>
> 인용 규약: base 인용에는 **규범 라벨을 병기**한다. 좌표(파일:행)는 작성
> 시점 값이고 문서는 움직인다 — authority 는 라벨이다. 토큰 비증식 규범은
> *번호가 아니라 이름으로* 부른다 (base §1.4.2 함정 「이 규범의 거처가 인용을
> 틀리게 만든다」 — 실측 열두 곳이 §1.4.6 으로 잘못 가리키고 있었다).
>
> **opcode 표기 규약**: opcode 는 12b 정식 표기 세 자리로 적는다 —
> `0x400`–`0x405` 는 물론 base 인용도 `0x014`·`0x016`·`0x019` 처럼 세 자리다
> (base §1.3.1 규범 「opcode 는 12비트다 — 개정됨」). **수치는 종전 8b 표기와
> 동일하다** (`0x014 == 0x14`).
>
> 니모닉 `CCMP*` 는 **확정된 이름**이다 (사용자 확정 2026-08-28) — 다른 확장
> 명세들이 니모닉을 작업명으로 남긴 것과 이 점이 다르다.

## 0. 확장의 형태 — 확정 요약

**채택 갈래 = 값-평면 비교.** 발화를 고르는 기구(steer)는 전 갈래 기각하고,
**값을 고르는 원료(비교 마스크)** 만 신설한다.

| 항 | 확정 형태 |
|---|---|
| 신규 opcode | **CCMP 6종 `0x400`–`0x405`** (배정안 — 최종 확정은 배정 절차 몫, §2.1) |
| 신규 EH | **0** |
| 신규 dtype | **0** |
| 신규 능력 부재 사건 | **0** · `CAP_STATUS` 증설 **0** |
| 인코딩 행 | `0x010 ADD` 행 **축자** — required `[port]` · forbidden `[mem, subscript]` · `allow_imm_xor_opref` · `rtl_alu_binary` (§2.2) |
| 결과 | **마스크 원형** — 참 = 전비트 1 · 거짓 = 전비트 0. 64b 단일 beat = 토큰 비증식 분할의 **②** (§3) |
| select | CCMP 1 + 3발화 = **4발화** (lowering-only 는 **8~9발화** — 공통 부분식 재사용이 성립하면 8, 재지 않았다 · §4.3 · §10 원장 4) |
| 신규 규범 | **「Ctrl 류는 EH ≥ 1」** — base §5.1 잔여 수용 1항의 보안 결정 입력에 대한 답 (§5) |
| 전건 | **없다 — W1·W3 는 착지 완료** (§1) |

경계선 정식화: **「고르는 것이 값이면 밖(적법), 발화이면 안(위반)」.** 발화의
유일한 원천은 호스트 명령 큐다 (base §2.3 규범 「발화의 유일한 원천은 호스트
명령 큐다」) — 술어가 발화 여부를 정하는 순간 그 규범의 근거 구조를 침식한다,
문면에 저촉되지 않더라도.

## 1. 전건 — 착지 완료

`Ctrl-min` 은 **base 정본 개정을 요구하지 않는다.** 제안 메모가 전건으로 세운
둘은 #25 인코딩 개정 파도에서 이미 착지했다 — 「전」이 아니라 **완료**다.

| 전건 | 지위 | 자리 |
|---|---|---|
| **W1 — opcode 12b** (`0x400` 은 이 파도 전에는 인코딩 자체가 없었다) | **착지 완료** (커밋 `b27b68b` 정본 · `62889e5` asm/ISA · `4a8da34` RTL·formal) | base §1.3.1 규범 「opcode 는 12비트다 — 개정됨」 |
| **W3 — 미배정 opcode = malformation** | **착지 완료** (같은 파도) | 같은 규범: 「*미배정 opcode 는 malformation 이다.* 예비 영역(`0x8##`–`0xF##`) 전체를 포함하며, 배정(claim)되기 전까지다」 |

**영역 구획** (base §1.3.1 규범 「영역 구획 — 배정 절차의 규범이다」):
`0x0##`–`0x3##` 기존 계보 · `0x4##`–`0x7##` **신규 확장용** · `0x8##`–`0xF##`
예비. `0x400`–`0x405` 는 신규 확장용 영역에서 받는다.

> **정정 하나** — 제안 메모 §10 항 3 은 정수 MIN/MAX 코드점 선점 불요의 근거를
> 「예비 영역은 W3 아래 자동 malformation」이라 적었다. 그 문장은 좁다:
> `0x406`·`0x407` 은 예비 영역이 아니라 **신규 확장용 영역**이다. 근거는 영역이
> 아니라 **미배정**이다 — W3 는 영역과 무관하게 claim 전의 모든 opcode 를
> malformation 으로 처분하므로, 자리를 미리 사 두지 않아도 그 자리는 보호된다.
> (같은 규범의 해설: 「영역은 관례이지 하드웨어 판정이 아니다 … 영역 니블이
> 슬그머니 dispatch 비트가 된다」.)

### 1.1 현행 실측 — ISA JSON 전수

`isa/wt64v1_isa.json` (`_schema_version: 1`) 실측:

- opcode **68종**. 전부 `0x0##` — 확장 니블 비0 opcode 는 현재 0종이다.
- **정수 *이항 스칼라* 비교 0건 · SIMD 레인 비교 0건.** `0x400`–`0x405` 는
  중복이 아니다. *「정수 비교가 실물에 없다」가 아니다* — 비교는 **감축 트리
  안에만** 있다: `reduce_op_codes = {"sum":0,"max":1,"min":2}` (`0x025 RED`,
  desc 축자 「RED (op in imm16[7:4])」) · `acc_reduce_op_codes =
  {"sum":0,"max":1,"l2sq":4,"mean":5}` (`0x072 ACC_REDUCE`). 아래 항이 인용하는
  `0x079 FMINMAX` notes 자신이 「the signed-int compare tree」로 *그 트리의
  존재*를 전제한다. 없는 것은 **두 값을 받아 술어(또는 선택값)를 내는 명령**
  이고, 그 자리를 CCMP 가 채운다.
- 인접한 것: AND/OR/XOR `0x014`–`0x016` · NOT/NAND/NOR/XNOR `0x050`–`0x053` ·
  NEG `0x01B` · SAR `0x019`(`require_imm16: true` — `SAR(x,63)` 이 1발화로
  적법) · STEER `0x002`(desc 축자 「STEER — pass-through with new tag」) ·
  MERGE `0x003`(desc 축자 「MERGE — merge alias of STEER」).
- **SIMD 정수 레인 블록** `0x060`–`0x065` 는 add/sub/mul 뿐 — 비교 없음
  (`…_WIDE_SCALAR` 셋 + `…_WIDE_VEC` 셋 · `0x060` desc 축자 「32xint4 lanes」).
  *fp 블록은 이 자리가 아니라 `0x070`–`0x07F` 다* (`fp_block._doc` 축자
  「0x070-0x07F mode-byte legality」) — §9.1 이 같은 범위를 「레인 기계
  (`0x060` 블록)」로 부르는 쪽이 이 문서의 옳은 이름이다. `0x079 FMINMAX` 의
  notes 는 「the signed-int compare tree is NEVER reused for FP — dedicated
  offset-key comparator」로 **FP 방향만** 못박는다.
- **EH 없는 명령의 현행 전수 = NOP 하나.** `asm_legality.required` 가 `[]` 인
  행은 `0x000 NOP` 하나이고, `0x001 WADV` 도 `required: ["port"]` 다. base
  §5.1 잔여 수용 1항의 「현행 ISA 전수에서 NOP 하나」와 일치한다.

## 2. CCMP 6종

### 2.1 코드점과 니모닉

| opcode | 니모닉 | 술어 |
|---|---|---|
| `0x400` | CCMPEQ | `a == b` |
| `0x401` | CCMPNE | `a != b` |
| `0x402` | CCMPLTS | `a < b` (signed) |
| `0x403` | CCMPLES | `a <= b` (signed) |
| `0x404` | CCMPLTU | `a < b` (unsigned) |
| `0x405` | CCMPLEU | `a <= b` (unsigned) |

- **배정안이다.** 사용자 승인은 났고(2026-08-28), **최종 확정은 배정 절차의
  몫**이다 — base §1.3.1 이 「배정의 정당화는 「자리가 남았다」가 아니라
  「필요가 먼저 확인됐고 이 자리가 유일 정합」이어야 한다」로 규범화했고, 그
  절차의 *거처*는 base B.5 미결(「확장 절차의 거처」)이다. 겹침 회피는 이미
  조정돼 있다 — `Txtsmp` 는 `0x41#` 를 청구한다
  (`.claude-memos/txtsmp_proposal.md`).
- **GT/GE 는 의사 니모닉이다** — 피연산자 교환으로 어셈블러 표면에서만
  제공하고 **코드점을 0개 소비한다.** 선례는 ISA JSON 의 `hl_only_mnemonics`
  4종(BATCHNORM_INFER · LAYERNORM · RESHAPE · RMSNORM)이며, 그 기구는
  macro 단계에서 전개되고 legality 단계에 도달하면 오류다
  (`asm/wavetensor_asm.py:1573`).

### 2.2 인코딩 행 — `0x010 ADD` 행 축자

ISA JSON 의 `0x010 ADD` 행을 **그대로** 복제한다 (실물 대조 완료):

```
asm_legality = {"required": ["port"],
                "forbidden": ["mem", "subscript"],
                "allow_imm_xor_opref": true,
                "require_opb_flag": false,
                "require_imm16": false}
rtl_legality = {"req_port": true, "req_mem": false, "req_subscript": false,
                "req_opref": false, "req_imm16": false,
                "forbid_subscript": true, "forbid_mem": true,
                "forbid_imm_any": false, "forbid_opref": false}
rtl_alu_binary = true
```

- **B 피연산자는 IMM XOR OPREF** — ADD 와 같은 규율이다. 이 행을 고른 이유는
  「비슷해서」가 아니라 이항 · 부작용 없음 · 64b 단일 결과라는 세 성질이 ADD
  와 같기 때문이고, 그 성질이 아래 §3·§5 의 판정을 그대로 물려받게 한다.
- **문서화된 비대칭 하나를 함께 물려받는다.** ISA JSON `_doc` 이 이름한 첫째
  비대칭 — 「asm skips required-port under allow_imm_xor_opref」 — 이 그것이다:
  어셈블러는 `allow_imm_xor_opref` 행에서 XOR 분기를 타고 `required` 루프를
  건너뛴다(`asm/wavetensor_asm.py:1593`). 따라서 **PORT 필수를 집행하는 것은
  어셈블러가 아니라 디코드 경계다** (`rtl_legality.req_port: true`). §5 의
  따름정리를 읽을 때 이 사실이 필요하다 — 그리고 그 통일은 이 확장의 몫이
  아니라 ISA JSON `_doc` 이 「an explicit v1.8.0b decision — do not silently
  "fix" one emitter」로 못박은 별건이다.
- EH 사슬 최악: BH(1) + CH(1) + PORT(1) + IMM64(3) = **6워드 · EH 2슬롯**
  (워드 수는 base §1.3.2 카탈로그 실측). base 상한 — 기본 형상에서 EH 최대
  4개 · 448b = 14워드 — 의 안이다 (base §1.3.1 규범 「최대 길이」).
- **`decode_reserved` 는 쓰지 않는다.** ISA JSON `_doc` 이 정의한 staging
  비트(행은 실리고 opcode 는 whitelist 에서 빠져 RTL 이 계속 decode_error)는
  「PE_Core arm 착지 전에 ISA 행이 먼저 나가야 하는」 경우의 것이다. 이 확장은
  RTL 재구현 이전이므로 그 창 자체가 없다 — 행과 실장이 같은 파도로 간다.

### 2.3 어셈블러 표면

- 6종 모두 `.port dest=N` + (`.imm64`/`.imm32`/`.imm16` XOR `.opref`) 형태.
- GT/GE 는 macro 단계 전개 — `CCMPGTS a, b` → `CCMPLTS b, a`. 전개 후 남는
  니모닉은 위 6종뿐이다.
- **의사 니모닉이 코드점을 사지 않는다는 사실은 문서가 아니라 기구가 지킨다** —
  `hl_only_mnemonics` 목록에 오르면 legality 단계 도달 자체가 오류다.

## 3. 결과 원형 — 마스크

### 3.1 규범 — 마스크 원형

> **CCMP 의 결과는 마스크다** — 술어가 참이면 **전비트 1**(`0xFFFF_FFFF_FFFF_FFFF`),
> 거짓이면 **전비트 0**. 다른 원형(0/1 불리언, 조건 코드 레지스터, 플래그
> 비트)은 이 확장에 없다.

근거는 취향이 아니라 소비처다 — §4 의 select lowering `r = XOR(b, AND(XOR(a,b), m))`
이 성립하는 유일한 원형이 전비트 마스크다. 0/1 불리언을 고르면 그 lowering
앞에 부호 확장 한 발화가 더 붙고, 조건 코드 레지스터를 고르면 **새 아키텍처
상태**가 생겨 「발화 사이 상태」를 만들지 않는다는 이 기계의 어법을 깬다.

### 3.2 ISA-9 판정 — 분할의 ②

토큰 비증식 규범(base §1.4.2 규범 「토큰 비증식 — 발화가 남기는 후속 전송
전량의 분할」)은 후속 전송 전량을 셋 중 정확히 하나로 둔다 — 없음 / 결과 슬롯
한 칸에 착지하는 **단일 beat 결과 하나** / 조각열 하나.

**CCMP 는 ②다.** 64b 마스크 하나가 결과 슬롯 한 칸에 착지한다. 조각열이
아니므로 base §4.3 의 다섯 조건도, 조각 축의 처분들도 이 확장에 걸리지 않는다.

**출력 매체도 함께 적는다** — base B.5 「확장의 *출력 매체*」 행(조건부: 해당
확장의 도입이 전건)이 요구한 것이다. CCMP 의 출력 매체는 **결과 슬롯 하나뿐**
이며 메모리 경로는 쓰지 않는다 (`forbidden: ["mem", ...]` · `forbid_mem: true`).
따라서 그 행이 경계한 우회 — 「출력을 메모리 경로로 두면 계수를 그대로
통과한다」 — 는 이 확장에서 인코딩으로 닫혀 있다.

## 4. 발화 수 — 공식 계수

### 4.1 lowering-only (CCMP 없이)

signed 전범위 LT 마스크를 현행 op 셋으로만 만들면:

```
d = SUB(a, b)
v = AND(XOR(a, b), XOR(a, d))
m = SAR(XOR(d, v), 63)
```

SUB · XOR · XOR · AND · XOR · SAR = **6발화**. (제안 메모 1차판의 「≈5」는
오계였고 적대 검토가 정정했다.) `0x019 SAR` 이 `require_imm16: true` 라
`SAR(x, 63)` 이 1발화로 적법한 것이 이 계수의 전제다.

**6 의 지위는 「검산한 최소」이지 「증명된 하한」이 아니다** — 적대 검토가 대안
공식 하나를 검산해 7발화를 얻었고 6 미만을 찾지 못했을 뿐, 현행 op 셋 위의
전수 탐색은 하지 않았다. 이 확장의 결론은 하한에 걸려 있지 않다.

### 4.2 select

마스크 `m` 위에서 `r = XOR(b, AND(XOR(a, b), m))` = **3발화**.

| 경로 | 발화 수 |
|---|---|
| lowering-only select | 6 + 3 = **9** |
| CCMP 경로 select | 1 + 3 = **4** |

### 4.3 이 수치의 지위 — 정직하게

- **공식 계수이지 워크로드 실측이 아니다** (§10 원장 3).
- **6 + 3 = 9 는 공통 부분식을 재사용하지 않은 셈이다.** 마스크 식과 select 식
  이 `XOR(a, b)` 를 공유하므로, 그 값을 한 번 만들어 두 소비자가 읽을 수 있으면
  **8** 이다. 재사용의 성립 여부는 결과 슬롯의 **소유 구간 $L$** 에 걸려 있고
  $L$ 은 파라미터로 남아 있다 (base §2.4 규범 「소유 구간 $L$ 은 파라미터다」 ·
  B.5). ⇒ **9 는 보수적인 상한이고 8 이 하한이다. 재지 않았다** (§10 원장 4).
  어느 쪽이든 CCMP 경로 4 와의 비교 결론은 바뀌지 않는다.
- 이 확장이 **없앤 발화 수**를 주장하지 않는다 — 실 워크로드에서 select 가
  얼마나 나오는지가 미측정이기 때문이다 (§10 원장 3).

## 5. 규범 — 「Ctrl 류는 EH ≥ 1」

### 5.1 물음

base §5.1 함정 「명명과 기전 사이의 창 — 닫혔다. 만료가 하나 남는다」의 마지막
문장이 이 절의 물음이다:

> 신규 확장(Ctrl 류)이 EH 없는 명령을 늘리면 1항의 폭이 함께 는다 — *EH 없는
> 명령으로 설계할지가 이제 보안 결정이다.* 그 확장의 설계 입력이다.

여기서 1항은 base §5.1 규범 「잔여 수용 — 부류 전수, 넷으로 닫힌다」의 첫째
항 — **EH 없는 명령**이다. CH 의 존재가 `next_hdr ≠ END` 에서 유도되므로 EH 가
0 인 명령은 CRC-32C 가 덮지 않고, 훼손이 양방향 모두 조용하다.

### 5.2 규범

> **`Ctrl` 계열의 모든 명령은 PORT EH 를 싣는다 — 따라서 EH ≥ 1 이다.**
> 이 확장은 EH 없는 명령을 **한 종도** 만들지 않는다.

### 5.3 따름정리다 — 설계 재량이 아니다

이 규범은 「그렇게 하기로 했다」가 아니라 **구조 귀결**이다. 세 문장에서
유도된다:

1. **토큰 비증식 규범**(base §1.4.2)의 분할은 후속 전송 전량을 「없음 / 단일
   beat 하나 / 조각열 하나」로 닫는다. CCMP 는 마스크 하나를 내므로 「없음」이
   아니다.
2. **수신자를 명명하는 자리는 PORT EH 본문 하나다** — base §1.4.1 규범 「출력
   태그 조립」: 「출력 태그의 노드 ID 필드는 `dest_node_id` 를 *그대로* 받는다」.
   그 값의 유일한 출처가 PORT EH 본문 `[15:0]` 이다(같은 절 규범 「비트 배치
   (축자)」).
3. 이 기계의 **순서 기전도 같은 자리에 선다** — base §4.4.4 규범 「무엇으로
   순서를 만드는가」가 순서를 *토큰 전달*로 만들고, 토큰은 수신자를 갖는다.
   wave 번호는 아무것도 게이트하지 않으므로 순서의 대체 통로가 아니다.

⇒ 값을 내는 명령은 수신자를 명명해야 하고, 명명의 자리가 EH 이므로 **EH ≥ 1
이 따라 나온다.** 「Ctrl 류를 EH 없이 설계할 수 있는가」는 선택지가 아니다 —
후속 전송이 「없음」인 Ctrl 명령은 마스크를 내지 않는 명령이고, 그것은 이
확장이 아니다.

**역방향 확인** (실측): EH 0 인 명령은 후속 전송이 「없음」인 명령뿐이라는
것이 ISA JSON 전수와 일치한다 — `required: []` 는 `0x000 NOP` 하나다 (§1.1).

**집행의 자리**: PORT 필수는 `rtl_legality.req_port: true` 로 **디코드 경계**가
집행한다 (§2.2 의 비대칭 참조 — 어셈블러는 `allow_imm_xor_opref` 행에서
`required` 를 건너뛴다). 다만 어셈블러 축에서도 EH 0 은 표현 불가능하다: XOR
분기가 `.imm*` 와 `.opref` 중 **정확히 하나**를 요구하므로 사슬이 비면 그
자리에서 거절된다. **두 축이 각각 다른 이유로 같은 결론에 선다.**

### 5.4 귀결 — 1항의 폭 증가 0

EH ≥ 1 ⇒ `next_hdr ≠ END` ⇒ CH 가 존재한다 (base §1.3.1 표 · §1.3.4) ⇒ CCMP
6종은 CRC-32C 가 덮는 부호어 안에 있다.

⇒ **base §5.1 잔여 수용 1항의 폭 증가는 0이다. 「현행 ISA 전수에서 NOP 하나」
는 이 확장 후에도 그대로 참이다.** 1항에 걸린 만료(기본 헤더 `[15:12]` CRC-4
갈래가 stable 동결과 함께 영구 소멸한다)의 시급성도 이 확장 때문에 오르지
않는다.

## 6. 상수 시간성 — 자명 이행이지 면제가 아니다

- **의무는 붙는다.** base §5.3 규범 「정의 — 절대치가 아니라 경로 간 동일성」의
  정의역은 전 명령에 걸린다. `Di` §1.4 가 그 정의역을 **(opcode, dtype, 서브옵)**
  으로 명시하자고 제안한 개정 초안의 관할 안에 CCMP 가 **든다** — dtype 축
  선례가 step 프로그램이 아닌 `0x070` 이라는 사실이 그 관할의 폭을 보인다.
- **이행은 자명하다.** CCMP 6종은 조합 회로 단일 beat 이고 서브옵도 dtype
  분기도 없다 — 술어별로 다른 상태열을 지날 자리가 인코딩에 없다. 술어는
  같은 비교기 출력의 서로 다른 해석이며, 데이터 의존 분기가 없다.
- **「대상이 아니다」로 적지 않는다.** 「step 프로그램이 아니므로 정의역 판정
  대상 자체가 아니다」로 적으면 상수 시간 의무가 안 붙는 것처럼 읽힌다. 의무는
  붙고, 이행이 자명하다 — 둘은 다르다.
- 형식화의 형태도 base 가 이미 정했다 (base §5.3 규범 「형식 속성도 같다 — 시간
  계약은 길이가 아니라 열로 적는다」): 상태열 *길이*가 아니라 상태열 *자체*의
  동일성으로 적는다. CCMP 의 6 술어 사이 miter 가 그 형태다 — 이 확장의 실장
  파도 몫이다.

## 7. 기각 전수 — steer 계열과 그 친족

되살리지 말 것. 각 갈래의 **사망 축이 서로 다르다** — 축을 옮겨 적으면 기각이
무너진다.

### 7.1 (a) 동종 이중 steer — 정적 malformation

두 PORT 팔(또는 두 ACCTGT 팔) 중 술어로 택일하는 형태.

base §4.2.3 규범 「종류별 반복 규칙 — 전수」가 **PORT 반복 = malformation**
(「수신자는 하나다. 다중 수신자는 multicast 설계 사항이고 이 설계에 없다」),
**ACCTGT 반복 = malformation**(「누산 대상은 하나」)로 처분한다. **디코드
경계에서 죽는다** — 의미 층에 도달하지 않는다.

### 7.2 (a′) 이종 쌍 steer — 정적으로는 적법, 의미 층에서 사망

술어로 「PORT 배달 / ACCTGT 누산」을 택일하는 형태.

> **§4.2.3 은 이것을 막지 않는다.** 반복 규칙이 금지하는 것은 *같은 종류*의
> 반복뿐이고, **PORT 1회 + ACCTGT 1회는 오늘 이미 다중 조각 wave 의 표준형**
> 이다 (`0x000 NOP` 하나를 뺀 전 opcode 가 PORT 필수 — §1.1 실측 · 총개수를
> 둘 이상으로 선언한 wave 에 ACCTGT 가 없으면 malformation — base §4.3 규범
> 「태그→구간 결속」 1항).

⇒ **(a) 의 사정권을 (a′) 에 옮겨 적지 말 것.** 이 갈래를 여는 개정의 사정권을
쓸 때 (a′) 에서는 **반복 표 두 행이 빠진다.**

기각의 실근거는 넷이고, 전부 의미 층이다:

1. **토큰 비증식** — 억제된 PORT 팔은 영원히 발화하지 않는 소비자다. 「발화가
   남기는 후속 전송 *전량*」의 분할이 「전량」에서 깨진다.
2. **base §4.3 결속 불변** — 「재조립 문맥이 *생성되는 시점*에 태그→구간(LBID)
   결속이 확정되고, 그 결속은 조각열이 종료할 때까지 *불변*이다」. ACCTGT 팔이
   데이터 의존이면 결속이 개시 wave 디코드 시점에 확정된다는 규범과 정면
   충돌한다.
3. **base §1.4.1 축자 조립** — 「출력 태그의 노드 ID 필드는 `dest_node_id` 를
   *그대로* 받는다 — 확장도 패딩도 없다」. 술어가 목적지를 고르는 자리가
   인코딩에 없다.
4. **타이밍 축** — 값 의존 배달 경로는 관측면이 된다 (base §5.1 위협 모델 3항
   「타이밍 채널」 · §5.3).

### 7.3 poison 술어화 — 기각 확정

base §1.4.4 규범 「poison 은 값의 신뢰도를 나른다」의 세 항과 정면 충돌한다:
「*전파는 논리합이다*」 · 「*poison 은 흐름을 바꾸지 않는다.* 경로도, 지연도,
발화 조건도, 중재 결과도, 수락 여부도 poison 에 의존하지 않는다. poison 은
게이트 입력이 아니라 ...」 · 명령 방향에서 「poison 은 *반드시 0* 이고 비0 은
거절 + loud fault 다」.

poison 을 조건 비트로 쓰는 갈래는 셋 전부를 어긴다. 게다가 저작자가 장치이므로
(태그 필드 중 유일하게) 호스트가 그 값을 술어로 쓰려면 신뢰 경계를 거꾸로
건너야 한다.

### 7.4 wave / 에포크 술어화 — 기각 확정

base §1.4.4 규범 「불투명 식별자 — wave 번호와 에포크」: 「기계는 이 둘을
*등가 비교와 보존* 외에 해석하지 않는다 — 산술, 비트 슬라이스, 해싱, 순서
비교, 게이트 입력으로 쓰는 것은 전부 금지다」. base §4.4.4 도 같은 방향으로
못박는다 — 「wave 번호는 *순서 기전이 아니다*」.

### 7.5 단일 opcode + imm16 서브옵 — 기각 (근거 둘)

- **①** 서브옵이 imm16 을 차지하면 즉치 B 피연산자 자리가 없다. `0x010 ADD`
  행의 `allow_imm_xor_opref` 규율 아래에서 B 는 IMM XOR OPREF 인데, imm 자리가
  서브옵에 팔리면 B 는 OPREF 전용이 되어 ADD 행 축자가 깨진다.
- **②** 탈출로(「imm16 서브옵 + imm32 로 B 를 싣는다」)도 죽는다 — base §4.2.3
  전수표가 **IMM16/32/64 를 한 종류로 묶어** 반복을 malformation 으로
  처분한다(「즉치가 여럿이면 어느 것인지 규정할 수 없다」). ②가 ①보다 더 닫힌
  기각이다.

⇒ 6 opcode 가 서브옵 니블보다 싸다. 이 판정은 `Di` 의 `0x07F ALGDi`(대수
opcode 하나 + imm16 서브옵 니블 둘)와 **반대 방향**인데, 두 확장의 B 피연산자
규율이 다르기 때문이다 — 섞어 읽지 말 것.

## 8. 부수 이득 — 한정해서 적는다

타일 축(`.claude-memos/graphics_tiling_axis.md`)에의 이득은 **「픽셀 ≥ 64b
형식에 한해」 값-평면 계산 도구를 공급**하는 것까지다.

- 그 메모 §4.4 의 실제 결손은 **계약 어휘** 결손이다 — 「이 칸은 안 덮였다」를
  나를 자리 없음 + 총개수 0 의 처분 0건. **CCMP 는 그 어느 것도 건드리지
  않는다.** (「빈 조각 값 채움」·「커버리지 마스크」라는 낱말은 그 메모에
  없다 — 전문 grep 0건, 재확인 완료.)
- **레인 평면에서 무너진다** — int4/int8 레인 포장 픽셀(레인 16개/8개)은 스칼라
  CCMP 로 레인 마스크를 만들 수 없고, 언팩–비교–리팩은 발화 수가 레인 수 배가
  된다. §9 항 1 이 그 자리다.

## 9. 그린 갈래 — 채택도 기각도 하지 않고 등재한다

### 9.1 SIMD 레인 CCMP 변종

§1.1 이 실측한 「레인 비교 0건」이 되돌아오는 자리다. 이 ISA 의 레인
기계(`0x060` 블록 · `0x06B GAMMA_MUL_W` · `0x078 DEQUANT`)와 타일 축을 보면
레인 술어가 가장 개연적인 실수요다.

**여기서 제안도 기각도 하지 않는다** — 미측정 원장 1(§10)이다. 수요를 재지
않았고, 재지 않은 채 코드점을 사면 §2.1 이 인용한 배정 규범(「필요가 먼저
확인됐고」)을 스스로 어긴다.

### 9.2 정수 2-입력 MIN/MAX (융합 비교-선택)

select 의 지배적 소비자는 통상 clamp/min/max 다 — CCMP + select 4발화 대 전용
opcode 1발화. `0x079 FMINMAX` 의 「정수 트리를 FP 에 재사용하지 않는다」 규약은
**FP 방향 한정**이므로 정수 MINMAX 를 막지 않는다.

- 코드점 후보 둘(`0x406`·`0x407`)을 **선점하지 않는다.** 미배정 opcode 는 이미
  malformation 이므로(§1) 자리를 사 두지 않아도 보호된다.
- **전례 없음이 아니다 — 기각 기록이 실물에 있다.** `0x072 ACC_REDUCE` 의
  notes 축자: 「MIN deliberately NOT shipped (RED=2 vs einsum=6 namespace
  collision dodged)」. 정수 MIN 배정은 과거에 **실제로 검토됐고 이름공간 충돌로
  기각됐다.** 그 기각 사유는 이 자리로 이전되지 않는다 — 충돌한 것은 *감축
  서브옵 값 공간*(`reduce_op_codes` 의 `min:2`)이고 여기서 노리는 것은 **이항
  스칼라 opcode** 이기 때문이다. 그러나 「선례 0건」으로 적으면 다음 사람이
  같은 검토를 처음부터 다시 한다.
- **미측정 원장 2**(§10) — clamp 빈도 실측이 채택의 전건이다.
- **base 쪽 D-09 와는 다른 절차다** — D-09 의 실제 빈칸은 `0x027`–`0x02F` 이고
  (`.claude-memos/extension_candidates.md` 실측 — 그 행의 「`0x26..0x2F` 여유」
  문면은 낡았다), 그것은 **base 배정**(`0x0##`)이다. 확장 배정(`0x4##`)과
  섞지 말 것 (base §1.3.1 영역 구획 — 「이 구획이 정하는 것은 *배정 절차*」).

| 4 | **lowering-only select 의 참값 8 인가 9 인가** (§4.3) | 상한 9 · 하한 8. 갈림은 결과 슬롯 소유 구간 $L$ 에 걸리고 $L$ 은 파라미터다 (base §2.4 · B.5) |
| 5 | **CCMP 의 면적·지연** | 재지 않았다 — 64b 비교기 하나라는 방향만 안다. 이 저장소에 실리콘·FPGA 실측은 한 건도 없다 (base B.4) |

## 11. 미결 — 사용자만 답할 수 있는 것

1. **최종 코드점 확정** — `0x400`–`0x405` 안은 승인됐고, 확정은 배정 절차의
   몫이다 (§2.1). 그 절차의 *거처*가 base B.5 미결(「확장 절차의 거처 —
   「명시적 개정」은 무엇을 밟는가」)이므로 이 항은 그 미결에 매달려 있다.
2. **`Ctrl` 계열의 확장 경계** — 「Ctrl 류」가 이 6종으로 닫히는가, 아니면
   §9 의 둘이 같은 확장 이름 아래로 들어오는가. 이름의 경계는 conformance
   flag 의 경계이기도 하다.
3. **conformance sub-flag 표면** — `C` 명세 §2.7 이 남긴 것과 같은 물음이다
   (`WT64v1-Ctrl/CCMP` 같은 flag 를 둘 것인가, 그 거처는 어디인가). 이 확장이
   그 물음을 새로 열지는 않으나 답을 앞지르지도 않는다.
4. **릴리스 축 · `T_stable` 지위 판정** — 이 문서의 완성이 이 미결을 닫지
   않는다 (지위 배너).

> **미결과 원장은 다르다.** 위 넷은 *사용자가 답할 것*이고, §10 의 다섯은
> *재야 답이 나오는 것*이다. 섞어 두면 회의를 기다릴 필요 없는 것이 회의를
> 기다린다 (base B.5 해설이 부류 오분류에 대해 이름한 형태).

## 12. base 정본에 남긴 것 — B.5 「소비 후 도착의 처분」

이 확장의 결속·재사용 축을 전수로 훑다가 정본의 빈칸 하나가 드러났다 — **결과가
소비된 뒤 같은 태그로 도착하는 전송의 처분이 정본 0건**이다.

전수 grep 재확인(정본 `chapters/` + `appendix/` 전량): 「소비 후」 **0건** ·
「소비된 뒤」 **1건** — base §4.3 규범 5항(「재조립이 완료되고 결과가 소비된
뒤의 같은 태그 재사용은 *적법*하다」) 하나뿐이고, 그 문장은 *호스트의 태그
재사용*을 허가할 뿐 *늦게 도착한 조각*을 처분하지 않는다. 「지각」·「늦게
도착」은 정본 전량 0건이다.

**등재 완료** — base 부록 B.5 「미결 결정」 표에 「소비 후 도착의 처분」 행을
신설했다 (지위: *미결* — 정본 자답 가능). 이 확장이 그 결손의 *원인*은 아니다.
CCMP 는 조각열을 만들지 않으므로(§3.2) 이 결손에 닿지 않는다 — 드러낸 것뿐이고,
그 사실을 여기 적는 이유는 base B.5 가 반복해 이름한 것 때문이다: **표를 만드는
행위가 그 표의 빈칸을 드러낸다.**
